# Обновление до 3.8

Сделайте согласованный backup базы и uploads, затем `python -m app.migrate` (миграция 0008 создаёт `helpdesk_state` и `helpdesk_links`, существующие данные не меняются). Мост остаётся выключенным, пока не задан `HELPDESK_PROVIDER` и ключ API в `.env`; после настройки пересоздайте app и worker. Откат ниже 0008 запрещён, если уже есть импортированные обращения Zendesk/Freshdesk: повторный импорт создал бы дубли. Подробности — [регламент моста](../docs/ru/SUPPORT_HELPDESK_BRIDGE_CURRENT.md).

Дистрибутив v28.25.0 добавляет вход `POST /email/inbound` для собственного приёмника почты магазина без миграций: задайте одинаковый `MAIL_INBOUND_SECRET` в `.env` магазина и Support Pro и пересоздайте app.

# Support Pro 3.6 — синхронизация после merge/split

Миграция 0006 сохраняет постоянные ID удалённых сообщений и версию структуры истории. При переносе в магазине worker пересопоставляет сообщения/файлы, закрывает объединённый источник и приостанавливает его старую очередь, сохраняя внутренние заметки. Нужен обновлённый магазин с 0062; сначала API, затем worker. До конца первого полного обхода не меняйте структуру старой переписки. Согласованный backup и проверка очереди обязательны. Старые исторические дубли автоматически не удаляются. [Полный регламент](../docs/ru/SUPPORT_REMOTE_HISTORY_CURRENT.md).

# Обновление до 3.5

Сначала сохраните согласованные backup базы и uploads. `python -m app.migrate` применяет 0005 с сохранением существующих данных; самостоятельный режим не меняется без SHOP_BRIDGE_URL. # Обновление до 3.4

Сначала выполните приведённую ниже процедуру резервного копирования. Для 3.3 → 3.4 применяется миграция 0004; данные предыдущих версий сохраняются. После обновления требуется повторный вход: старые cookie не содержат идентификатора серверной сессии.

Добавьте в сохранённый `.env`: WEBHOOK_ALLOWED_HOSTS (доверенные домены через запятую), CLAMAV_HOST, CLAMAV_PORT=3310, REQUIRE_ANTIVIRUS=false и METRICS_TOKEN. Не заменяйте старые секреты. Вебхуки без разрешённого домена будут попадать в ошибки.

Для сканирования: `docker compose --profile antivirus up -d`, затем CLAMAV_HOST=clamav и REQUIRE_ANTIVIRUS=true с пересозданием app/worker/bot. До готовности сигнатур ClamAV загрузки будут отклоняться.

В существующем nginx отключите access_log для путей `/portal/access/` или примените журналирование без URL-токенов. Новый Dockerfile отключает access-лог uvicorn. Секретные ссылки нельзя публиковать.

Миграция создаёт индексы FTS обычным CREATE INDEX: на большой БД запланируйте окно обслуживания. После обновления проверьте `/ready`, тестовую веб-заявку и доставку очереди. Установите команды и роли в `/operations`; старые тикеты и операторы остаются в общей очереди.

Новый backup-service копирует uploads и вызывает restore-check во временной БД; ему нужны права CREATE DATABASE. Для ручной проверки: `docker compose exec backup sh /restore-check.sh /backups/ИМЯ_КОПИИ`. Проверка не восстанавливает рабочую БД поверх существующей. В этой среде PostgreSQL/Docker недоступны, поэтому этот сценарий необходимо выполнить на сервере.

# Обновление Support Pro 2.1 → 3.0

Не запускайте установщик поверх работающей версии. Сначала сделайте резервные копии, затем перенесите код. Все команды ниже выполняются на вашем сервере; в рамках подготовки архива они не выполнялись.

## 1. Сохраните имя проекта и конфигурацию

Проверьте существующее имя Compose через `docker compose ls` и имена volumes. Если старая установка была в `/opt/support-pro-2` без `-p` и без COMPOSE_PROJECT_NAME, имя обычно `support-pro-2`.

Новая конфигурация явно использует `${COMPOSE_PROJECT_NAME:-support-pro-2}`. В `.env` задайте **точное старое имя**, иначе Docker создаст другие volumes, и панель будет выглядеть пустой. Не выполняйте `docker compose down -v`.

Сохраните существующие `.env`, `nginx/nginx.conf`, `nginx/certs`, `nginx/certbot` и каталог `backups`. Не заменяйте их примерами из архива.

## 2. Остановите обработку и сделайте копии

Из старого каталога установки, например:

```bash
cd /opt/support-pro-2
umask 077
mkdir -p backups
# Для исходной версии 2.1:
docker compose stop app bot nginx
# Если у вас уже был отдельный worker, также остановите его до копирования.
docker compose exec -T db sh -c 'PGPASSWORD="$POSTGRES_PASSWORD" exec pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > backups/before-3.0.dump
# Образ старого app должен быть уже собран; этот запуск выполняет только tar.
docker compose run --rm --no-deps --entrypoint tar app -C /data/uploads -cf - . > backups/uploads-before-3.0.tar
tar --exclude='./backups' -czf backups/code-before-3.0.tar.gz .
```

Убедитесь, что команды завершились успешно и копии не пустые. Проверьте структуру дампа:

```bash
docker compose exec -T db pg_restore --list < backups/before-3.0.dump
```

Перенесите копии за пределы сервера. Архив кода включает `.env` и сертификаты; храните его как секрет. Для повторного обновления используйте другие имена резервных копий, не перезаписывайте предыдущие.

## 3. Замените только код и конфигурацию сборки

Распакуйте новый архив в отдельный каталог. Из каталога установки:

```bash
SUPPORT_SOURCE=/путь/к/распакованному/support_pro_3_4
cp -a "$SUPPORT_SOURCE/app" "$SUPPORT_SOURCE/alembic" "$SUPPORT_SOURCE/scripts" .
cp "$SUPPORT_SOURCE/docker-compose.yml" "$SUPPORT_SOURCE/requirements.txt" "$SUPPORT_SOURCE/alembic.ini" "$SUPPORT_SOURCE/VERSION" .
cp "$SUPPORT_SOURCE/README.md" "$SUPPORT_SOURCE/UPGRADE.md" "$SUPPORT_SOURCE/TEST_REPORT.md" .
cp "$SUPPORT_SOURCE/.dockerignore" .
```

Добавьте в сохранённый `.env` отсутствующие настройки (старые секреты не меняйте):

```dotenv
COMPOSE_PROJECT_NAME=точное-старое-имя
PUBLIC_ORIGIN=https://ваш-домен
COOKIE_SECURE=true
MAX_UPLOAD_MB=50
AI_BASE_URL=
AI_API_KEY=
AI_MODEL=
```

Остальные переменные исходной сборки совместимы. ИИ можно настроить позже. Nginx должен проксировать WebSocket Upgrade и передавать `Host`, `X-Forwarded-Proto`, `X-Forwarded-For`. Для стандартного лимита 50 МБ задайте `client_max_body_size 52m`, чтобы помещался multipart-запрос.

## 4. Примените миграцию

```bash
docker compose build
docker compose up -d db redis
docker compose run --rm migrate
```

Мигратор поддерживает три состояния:

1. Пустая БД: создаёт исходную схему и затем расширяет её.
2. БД с Alembic `0001`: добавляет новые поля и таблицы без удаления истории.
3. БД без записанной версии: сравнивает таблицы, колонки, типы, nullable, первичные/внешние ключи и уникальные ограничения с исходной схемой 2.1. Только при точном совпадении помечает её `0001` и обновляет. При несовпадении останавливается до изменений. Не выполняйте `alembic stamp` вслепую.

Если миграция завершилась ошибкой, не запускайте новую панель до выяснения причины. Сохранённые копии позволяют восстановить старую систему.

## 5. Подготовьте права на старые файлы и 2FA

Новый app работает от UID 10001:

```bash
docker compose run --rm --no-deps --user 0 app chown -R 10001:10001 /data/uploads
docker compose run --rm --no-deps app python -m app.cli init
```

`init` сохраняет настроенные пароль и TOTP. Если у старого администратора нет 2FA, команда создаст и покажет ключ. Запишите его в приложение-аутентификатор до входа.

## 6. Запустите и проверьте

```bash
docker compose up -d app bot worker backup nginx
docker compose ps
docker compose logs --tail=100 app bot worker migrate
curl --fail https://ваш-домен/health
```

Проверьте на тестовом клиенте: текст и фото из Telegram; ответ и вложение из панели; внутреннюю заметку (её не должно быть у клиента); создание отдельного вопроса; закрытие и оценку; доступность старых файлов. Настройте рабочее время и доступность операторов.

## Что происходит со старыми данными

- Сохраняются операторы, категории, шаблоны, обращения, сообщения, вложения и журнал.
- Карточки клиентов создаются из имеющихся обращений. Старые сообщения клиентов становятся непрочитанными для операторов до открытия соответствующей карточки.
- Старые ответы оператора получают состояние `legacy`: исходная версия не сохраняла подтверждение Telegram, поэтому успешная отправка не выдумывается. Они **не попадают в очередь повторной отправки**.
- Автор старого ответа остаётся неизвестным, если его не было в исходной таблице.
- Даты подтверждённого первого ответа не восстанавливаются догадками. Существующие сроки решения сохраняются, новое поле срока первого ответа остаётся пустым. Для новых обращений SLA работает сразу; смена приоритета старого обращения рассчитает сроки от его исходной даты создания.
- Старые сессии не содержат версии авторизации: операторы должны войти заново.

## Откат

Миграция не предлагает разрушительный `downgrade`. Для отката остановите новые `app`, `bot`, `worker`, `nginx` и `backup`; восстановите старый код и конфигурацию, БД из `before-3.0.dump` в пустую базу и содержимое volume uploads из `uploads-before-3.0.tar`. Затем запускайте старую версию. Данные, появившиеся после резервной копии, нужно предварительно сохранить отдельно. Не запускайте старый код одновременно с новым worker.
