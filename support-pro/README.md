## Рабочие сценарии 3.4

- Роли: admin (все команды), manager (работа с обращениями и отчёты своей команды), senior_operator/operator (работа с обращениями своей команды), viewer (чтение), auditor (чтение и отчёты своей команды). Системные изменения доступны только admin. Команда без номера — общая очередь, а не доступ ко всем командам. Проверки выполняются на сервере, включая вложения, WebSocket, CSV и массовые изменения.
- `/operations`: команды, роли, календари, праздники, сохранённые фильтры, отзыв своих сессий; администратору также доступен журнал последних 100 задач и повтор ошибок.
- События пишутся в outbox в одной транзакции с тикетом/сообщением. Worker создаёт отдельные задания вебхуков и правил. После перезапуска доставка продолжается. Вебхуки: 8 попыток с задержкой до часа, lease 2 минуты, dead-letter и ручной повтор. Доставка at-least-once: получатель обязан удалять дубли по `Idempotency-Key`. HMAC-SHA256 подписывает точные байты тела (`X-Support-Signature: sha256=...`). Хост получателя должен быть явно доверенным в `WEBHOOK_ALLOWED_HOSTS`; управление DNS такого хоста тоже должно быть доверенным. Редиректы отключены.
- Правила выполняются транзакционно, проверяют условия status/priority/channel/team_id; действия status/priority/assign_to/notify. Неверные задания попадают в журнал ошибок. Изменения тикета самими правилами не запускают каскад новых правил. События: ticket.created, ticket.updated, message.created, message.sent, sla.warning, sla.overdue, call.created. Условия проверяют состояние на момент обработки.
- SLA: общий календарь и расписания команд, рабочие исключения, часовые пояса/DST. В pending отсчёт приостанавливается; при возобновлении сохраняется оставшееся рабочее время. Настройки календаря применяются к новым обращениям и при смене приоритета/команды; старые сроки массово не пересчитываются.
- Поиск использует PostgreSQL FTS с русской морфологией и GIN-индексами, сохраняя поиск по номеру и подстроке. На SQLite используется поиск по подстроке. Массовые статусы, назначения, теги, перевод в команду; сохранение фильтров; упоминания @login во внутренних заметках. Объединение требует предварительного просмотра и проверяет, что записи не изменились.
- `/portal`: анонимный веб-чат с собственной защищённой историей, вложениями и обновлением каждые 15 секунд при пустом поле ввода. Посетитель получает случайную ссылку восстановления на 30 дней. Администратор может выдать ссылку на историю существующего клиента на 7 дней и отозвать доступ. Это доступ по секретной ссылке, а не подтверждение личности через email. Внутренние заметки скрыты. Ссылки следует передавать только проверенному получателю и не записывать в access-логи.
- `/incidents`: подсказки похожих тем (до 200 последних открытых обращений), группировка вручную, число клиентов, редактируемый черновик и подтверждение общей отправки. Повторное подтверждение одной редакции не создаёт повторных сообщений.
- Проверка вложений через ClamAV INSTREAM. Если антивирус настроен, его сбой блокирует файл. Без `CLAMAV_HOST` проверка отключена, пока `REQUIRE_ANTIVIRUS=false`. Для обязательной проверки включите профиль antivirus, задайте CLAMAV_HOST=clamav и REQUIRE_ANTIVIRUS=true.
- `/live`, `/ready`, `/metrics`: состояние приложения, БД, Redis, worker и очередей. Для сборщика метрик доступен Bearer-токен METRICS_TOKEN; без него нужен вход администратора.
- Ежедневная резервная копия содержит дамп БД и uploads с SHA256. Скрипт восстанавливает дамп во временную отдельную БД и сверяет наличие файлов; только после успеха копия получает окончательное имя. Для этого нужны права создания временной БД. Копии не удаляются автоматически: настройте срок хранения и внешнее копирование под свой объём данных.

Проверки и ограничения окружения — в `TEST_REPORT.md`. Порядок обновления — в `UPGRADE.md`.

## Новая установка

Нужны Linux, Docker Engine с Compose v2, `python3`, `certbot`, домен с DNS на сервер и доступные порты 80/443. Нужен настоящий `BOT_TOKEN`, выданный BotFather.

```bash
sudo bash install.sh
```

Установщик по умолчанию использует `/opt/support-pro-2`, генерирует секреты, применяет миграции, создаёт администратора, показывает ключ TOTP и получает HTTPS-сертификат. Сохраните пароль и TOTP в менеджере паролей/аутентификаторе. При ошибке получения сертификата установщик останавливается: вход по HTTP не открывается.

Существующую установку скрипт не перезаписывает. Для неё используйте **UPGRADE.md**.

### Ручной запуск

```bash
cp .env.example .env
# Заполните секреты, BOT_TOKEN, DOMAIN и PUBLIC_ORIGIN=https://ваш-домен.
chmod 600 .env
docker compose build
docker compose up -d db redis
docker compose run --rm migrate
docker compose run --rm --no-deps app python -m app.cli init
docker compose up -d app bot worker backup
# Настройте HTTPS reverse proxy; nginx/nginx.conf в архиве — только bootstrap.
```

`ADMIN_PASSWORD` нужен для первоначального создания администратора. Повторный `init` сохраняет существующий пароль и настроенную 2FA. Если у старого администратора нет TOTP, `init` создаёт и показывает его.

### Восстановление доступа

На доверенном сервере:

```bash
docker compose run --rm --no-deps app python -m app.cli reset-2fa admin
docker compose run --rm --no-deps app python -m app.cli reset-password admin
```

Обе команды отзывают старые сессии. Настройки 2FA нового оператора показываются администратору один раз в панели создания команды. Передайте их оператору по защищённому каналу.

## Настройка ИИ

В `.env` задайте:

```dotenv
AI_BASE_URL=https://адрес-провайдера/v1
AI_API_KEY=ваш-ключ
AI_MODEL=имя-модели
```

Провайдер должен принимать `POST {AI_BASE_URL}/chat/completions` с `model`, `messages`, `max_tokens` и возвращать `choices[0].message.content`. Ключ передаётся как Bearer token. После изменения выполните `docker compose up -d --force-recreate app`.

Передаются тема и последние 40 сообщений клиента/операторов, максимум 24 000 символов переписки. Внутренние заметки, файлы и заметки из карточки клиента не отправляются. Имена или другие персональные данные могут присутствовать в самих сообщениях. Доступ к кнопкам включается только при заполнении всех трёх переменных. Черновик вставляется в поле ответа; оператор проверяет и отправляет его сам. Ограничение — один запрос на оператора каждые 30 секунд.

## SLA и отчёты

По умолчанию рабочая неделя — понедельник–пятница, 09:00–18:00 UTC. Измените расписание в разделе «SLA». Праздники и разрывные/ночные смены пока не поддерживаются; круглосуточный режим — все дни, 0–24.

Сроки отсчитываются от создания обращения. Статус «Ждём клиента» не останавливает срок решения. Новое сообщение клиента возвращает такой тикет в работу. Смена приоритета пересчитывает сроки от исходной даты, поэтому не обнуляет уже потраченное время. Изменение общих настроек не переписывает сроки существующих тикетов. Ручное повторное открытие сохраняет первоначальный SLA.

В отчётах выборка обращений строится по дате создания. Среднее время — календарные минуты; соблюдение SLA сравнивается с рассчитанным рабочим дедлайном. Открытые просроченные обращения входят в нарушения, ещё не наступившие сроки без результата не входят в знаменатель. Метрика «Открыто сейчас» учитывает все даты. Ответы операторов считаются по дате подтверждённой отправки. `sent` подтверждает принятие Telegram, а не прочтение клиентом.

## Работа команды

Все активные операторы работают в общей очереди и имеют доступ ко всем клиентам, обращениям и заметкам. Назначение определяет ответственность и получателя уведомлений, но не является разграничением доступа. Управление командой, SLA, справочниками, отчётами и журналом доступно администраторам.

Отключение оператора отзывает сессии, но не переносит его открытые обращения автоматически: используйте общий список с фильтром по оператору. Индикатор набора — информационный; два оператора всё ещё могут отправить разные ответы. Черновик хранится в sessionStorage вкладки и привязан к оператору и тикету; файл после обновления страницы нужно выбрать заново.

При разделении тикета переносятся только отмеченные сообщения клиента и их вложения. Ответы команды остаются в исходной переписке. SLA нового тикета отсчитывается от самого раннего перенесённого сообщения. Текущим обращением клиента становится новое; клиент может выбрать другое через `/tickets`.

## Эксплуатация

- Запускайте один экземпляр `bot` (long polling) и один `worker`. Web-приложение можно масштабировать; события передаются через Redis. Схема нагрузки нескольких workers отдельно не проверялась.
- `/health` проверяет БД, Redis и heartbeat фонового обработчика; отсутствие heartbeat даёт 503.
- `MAX_UPLOAD_MB=50` ограничивает файлы приложения. Доступность загрузки конкретного файла также зависит от ограничений Telegram Bot API; при отказе отображается ошибка. Если меняете лимит приложения, согласуйте его с `client_max_body_size` Nginx; оставьте запас для multipart.
- Очередь и уведомления хранятся в PostgreSQL. Redis используется для real-time, presence, rate limiting и heartbeat. При недоступном Redis вход временно закрывается.
- Повтор при явном ограничении частоты Telegram планируется автоматически, до пяти попыток. Ошибки запроса и неопределённые сетевые исходы требуют ручного решения.
- Контейнер backup ежедневно пишет проверяемый custom-format `pg_dump`, хранит 14 дней и не сохраняет незавершённый дамп как успешный. Он не копирует файлы вложений.
- Делайте внешний backup PostgreSQL, Docker volume `uploads`, `.env` и сертификатов. Проверяйте восстановление.
- Для обновления сертификата запускайте ежедневно от root `bash /opt/support-pro-2/scripts/renew-cert.sh`. Например, настройте cron или systemd timer на своём сервере.
- Секреты и `.env` не входят в Docker image. Для production оставляйте `COOKIE_SECURE=true` и точный HTTPS `PUBLIC_ORIGIN` без завершающего `/`.
