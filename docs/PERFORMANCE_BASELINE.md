## Воспроизводимое окружение

Workflow `.github/workflows/load-security.yml` использует Ubuntu24.04 runner, собирает локальный стек через `scripts/test-up.sh` и запускает:

```bash
k6 run --summary-export k6-summary.json tests/load/shop.js
```

`API_BASE=http://127.0.0.1:18080`. В `docker-compose.test.yml` работают backend/worker, PostgreSQL18.6 и Redis8.10 с закреплёнными digest, тестовые web-контейнеры admin/cabinet/miniapp. Порты 18080–18083 привязаны к loopback. Включены `APP_ENV=test`, `PAYMENTS_SANDBOX=true`; `COOKIE_SECURE=false` относится к локальному HTTP-стеку.

Caddy/TLS, Support Pro, настоящих платёжных касс, Telegram и Remnawave в этом стеке нет. Не фиксировались CPU/RAM конкретного production-сервера, размер production-базы, мобильная сеть, внешняя задержка и холодный старт. Поэтому аппаратную конфигурацию VPS и показатели этих систем по этому прогону не выводим.

Setup регистрирует четыре тестовых пользователя `example.test` и выбирает первый тариф. Это небольшой набор данных, не воспроизведение объёма клиентской базы.

**Смысл успешного ответа:** скрипт объявляет ожидаемыми HTTP200–299, 409 и429. Проверки каталога и sync принимают200/429; checkout —200/409/429. Следовательно, `http_req_failed=0` не означает, что каждый запрос получил бизнес-результат200. В итоговом журнале нет разбивки по статусам, и по нему нельзя отделить полезную пропускную способность от срабатываний rate limiter. Checkout не означает15 реальных оплат, а возможность выполнить sandbox complete зависит от ответа create.

## Безопасность и хранение доказательств

Тот же run выполнил OWASP ZAP baseline для публичного config API и кабинета без Caddy. Сводка: High0, Medium2, Low3, Informational3. Среди предупреждений — заголовки CORP/COEP и wildcard CSP. Учитываются исключения `.zap/rules.tsv`; зелёный workflow не является заключением об отсутствии уязвимостей или полным security-аудитом.

Артефакт workflow `load-security-reports` содержит `k6-summary.json` и ZAP HTML/JSON; срок доступности ограничен GitHub retention. Workflow выводит округлённую аннотацию через `scripts/ci/k6-summary.py`; таблица выше использует более точные строки job. Не сохранять полный вывод `test-up.sh` в публичный отчёт: он содержит создаваемые учётные данные тестового администратора. В этом документе приведены только численные результаты и несекретные параметры сценария.

## Как сравнивать следующие изменения

Сравнивать следует тот же `tests/load/shop.js`, тот же состав стека и объём данных, явно записывая новый commit/run. Один CI-прогон не позволяет объявить устойчивую регрессию или ускорение: runner и фоновые условия меняются. Изменение сценария, порогов, обработки429 или данных делает сравнение отдельным экспериментом.

Workflow нагрузки отделён от основного `CI gate`; изменение порога здесь не добавляет обязательный gate автоматически. При этом для PR проверяются все применимые результаты согласно правилам проекта. Численные пороги сценария не являются production SLO.
