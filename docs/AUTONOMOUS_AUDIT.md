# Автономный аудит: полный перечень и проверка согласованности

Требования REQ-QA-0024–0027 сохраняются полностью. Текущий запуск проверяет согласованность источников и документов; полный продуктовый аудит ещё не реализован. Успех этого workflow не означает завершение всех требований или готовность к публикации.

Команда: `python scripts/audit/run_full_audit.py`. Строгий режим `--require-ready` дополнительно возвращает ошибку при незавершённых требованиях или неподтверждённых флагах манифеста.

## Что выполняется

| Проверка | Реальное условие |
| --- | --- |
| Реестр | Канонические формулировки, ID, диапазоны и SHA соответствуют реестру; статусы и пути доказательств проверены |
| Матрица источников | Все записи источника представлены в актуальной матрице без выдуманных связей |
| Карта файлов | Документ соответствует отслеживаемым файлам |
| Заметки о выпуске | Выполнен структурный контракт нового changelog; опубликованные исторические версии сохранены |
| Ссылки документации | Локальные ссылки и якоря проверены существующим валидатором |
| Runtime | Запущен существующий поиск запрещённых заглушек |
| Секреты | Запущен существующий сканер отслеживаемых файлов; значения находок не выводятся |

Каждая команда имеет настоящий код выхода, длительность и отдельный лог. Ненулевой код, тайм-аут и ошибка запуска приводят к FAIL аудита. Отчёты сохраняются и при сбое одной из проверок. Известные значения секретов из переменных окружения, HTTP credentials и заголовки авторизации скрываются в сохраняемых логах; произвольные production-логи этот инструмент не читает.

## Результаты запуска

| Файл | Содержимое |
| --- | --- |
| `artifacts/audit/checklist-results.json` | Полный канонический текст каждого требования, диапазон, SHA, продукт, заявленный статус, примечание, объявленные evidence и отдельные фактические результаты команд |
| `artifacts/audit/FULL_AUDIT_REPORT.md` | Таблицы команд и статусов, полный перечень ID, ошибки и ограничения |
| `artifacts/audit/logs/*.txt` | Логи выполненных команд после фильтрации |

Workflow запускается для PR, при push в main, вручную и по расписанию. Он создаёт отчёт и логи во время работы. Шаг загрузки выполняется и при сбое аудита. GitHub хранит загруженные файлы 14 дней. Отчёт также доступен в сводке запуска. После истечения срока хранения нужен новый запуск. Идентификаторы запуска и коммита в отчёте позволяют отличать версии.

## Плановые запуски и фактическое выполнение

В GitHub Actions выберите нужный процесс и отфильтруйте запуски по событию `schedule` и ветке `main`. Время в расписании задано в UTC. GitHub может поставить запуск в очередь с задержкой. Выполнение подтверждают назначенный runner, фактическое время начала и результат нужного шага в журнале задания. У задания в очереди результата ещё нет. Оба процесса также поддерживают ручной запуск через `workflow_dispatch`. ## Границы доказательств

Заявленный PASS в реестре не становится результатом проверки этого запуска. Поле `execution_in_this_audit` у требования остаётся null. Неизвестные критерии, зависимости и релизные связи остаются null или пустыми; исходная формулировка не сокращается.

Отчёт содержит фактические commit, branch (null при detached HEAD), workflow ref, UTC timestamp и версии Python/Git. Счётчики продуктовых тестов и skipped tests остаются null: этот workflow не запускает весь backend, браузерные, мобильные и инфраструктурные тесты. Скриншоты и внешние artifact links не выдумываются. Эти доказательства нужно отдельно связать с точным кандидатом.

Список проверок не подменяет все специализированные скрипты из исходного промпта. Реальные платежи, VPN, устройства, VPS, сборки и подписи требуют отдельных запусков. Полная релизная приёмка: [RELEASE_READINESS.md](RELEASE_READINESS.md). Все исходные задачи: [REQUIREMENTS_MASTER_REGISTER.md](REQUIREMENTS_MASTER_REGISTER.md).
