# Табличный changelog каждого нового релиза

Требование владельца от 17.11.2026: REQ-DOC-0038. Для каждого нового релиза обязателен аккуратно оформленный changelog без грамматических и орфографических ошибок, с подробным описанием всех изменений в таблице.

## Содержание и оформление

В `CHANGELOG.md` создаётся раздел `# vX.Y.Z`. В заметках GitHub Release используются те же строки таблицы в том же порядке. Для удобства чтения изменения можно разбить на таблицы по продуктам: клиент, магазин и кабинет, админка, серверные компоненты и инфраструктура, документация и зависимости. Каждая таблица имеет одинаковые колонки:

| Колонка | Что необходимо описать |
| --- | --- |
| Область | Продукт, компонент или затронутая платформа |
| Изменение и причина | Что добавлено или исправлено и какую задачу это решает |
| Подробности | Существенные детали; поведение до и после изменения; условия, при которых оно проявляется |
| Влияние и действия | Что увидит пользователь или администратор; совместимость; необходимые действия, миграции и ограничения |
| Проверка | Реальные команды, результаты и среда; ссылка на CI при наличии; непроверенное обозначается прямо |
| PR / коммит | Ссылка на существующий PR или коммит именно в этом репозитории |

Писать полными понятными фразами, без склеенных слов и необъяснённых сокращений. Одно самостоятельное изменение — одна строка; связанные технические детали можно объединить без потери смысла. Для новой возможности явно указать, что раньше её не было. Если действий или миграций не требуется, написать это словами. Символ вертикальной черты внутри ячейки экранировать обратной косой чертой. Не оставлять пустые ячейки, заглушки и формулировки вроде «разные улучшения».

Готовый каркас: [RELEASE_CHANGELOG_TEMPLATE.md](templates/RELEASE_CHANGELOG_TEMPLATE.md). Разделы «Ломающие изменения», «Миграции», «Откат», «Известные ограничения» и «Чем проверено» в заметках выпуска сохраняются по REQ-CI-0011.

## Обязательная подготовка перед публикацией

1. Сверить все изменения между предыдущим опубликованным тегом и точным кандидатом выпуска: объединённые PR, отдельные коммиты, исправления, функции, изменения API и схемы данных, зависимости, сборку, CI, инфраструктуру и документацию. Каждое самостоятельное изменение должно попасть в таблицу; не заменять этот шаг перечнем только заметных функций.
2. Вычитать весь новый раздел и заметки выпуска: грамматику, орфографию, пунктуацию, согласование слов и терминов. Команды, пути, версии, URL и имена собственные сверить с исходниками. Проверка словарём дополняет вычитку и не подтверждает её автоматически.
3. Проверить ссылки, согласованность таблиц, результаты тестов и ограничения. Не переносить зелёный результат с другого коммита и не объявлять непроверенную production-работу подтверждённой.
4. Проверить таблицы в отображении Markdown: заголовки, читаемость, отсутствие случайного деления ячеек, полноту строк. Перед публикацией не должно оставаться заглушек.

## Автоматический барьер

Команда: `python scripts/audit/check_release_changelog.py`. Она включена в обязательную проверку документации CI и в подготовку публикации перед созданием тега и релиза.

Для нового тега проверка требует подробную таблицу, все шесть колонок, непустые описания, ссылки на PR или коммиты, отсутствие заглушек и дублей, совпадение строк в changelog и заметках выпуска, точный тег и обязательные эксплуатационные разделы. Регрессии: `tests/test_release_changelog.py`.

Это проверка структуры и согласованности. Она не доказывает полноту относительно diff, корректность всех формулировок, грамматику, действительность результатов или качество отображения. Эти пункты остаются обязательной частью подготовки релиза и приёмки REQ-DOC-0038.

## Уже опубликованные выпуски

v28.161.0 опубликован до нового поручения и исключён только из нового требования к структуре. Исторические заметки, теги, релизы и артефакты не переписываются. Исключение зафиксировано в коде ровно для v28.161.0 и не вычисляется из текущего манифеста. Каждый другой будущий тег должен пройти новый барьер. Версии ради внедрения этого правила не повышаются.

## Отдельные выпуски VPN-клиента

Правило также распространяется на каждый новый тег `client-vX.Y.Z`. Его заметки хранятся в `docs/releases/client-vX.Y.Z.md`, а соответствующая таблица — под тем же заголовком в `CHANGELOG.md`. Общая проверка CI проверяет новую версию клиента из Gradle; только уже опубликованная 1.10.1 сохранена как историческое исключение.

Дополнительно шаг создания клиентского GitHub Release вызывает `python3 scripts/audit/check_release_changelog.py --client-version X.Y.Z` непосредственно перед созданием выпуска. В тело входят подготовленные подробные заметки, затем сведения об APK. Для любого нового клиентского выпуска этот путь требует таблицу даже при историческом номере версии; уже существующие клиентские заметки не переписываются. Регрессии запускают реальный Python-парсер из сценария публикации на файловых примерах, не публикуя релизы.
