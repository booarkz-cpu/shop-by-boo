# Безопасное объединение аккаунтов

Объединение переносит данные одного клиентского аккаунта в другой. Исходный аккаунт становится необратимым служебным указателем на основной, а его способы входа продолжают открывать основной аккаунт. Операция доступна самому клиенту в разделе **Безопасность → Объединение аккаунтов** и не выполняется администратором без подтверждения обеих сторон.

## Порядок для пользователя

1. Войдите в аккаунт, данные которого нужно перенести.
2. Откройте «Безопасность», раскройте первый шаг и подтвердите владение текущим паролем. Для OAuth-only аккаунта нужен вход, созданный не более пяти минут назад.
3. Создайте и скопируйте одноразовый код. Он действует десять минут, показывается только в ответе и хранится в базе как SHA-256.
4. Выйдите и войдите в аккаунт, который должен остаться основным.
5. Вставьте код, нажмите «Показать план переноса» и изучите суммы, количества и конфликты. Preview ничего не изменяет.
6. Если план разрешён, подтвердите основной аккаунт его паролем либо свежим OAuth-входом, отметьте согласие и нажмите «Объединить аккаунты».
7. После успеха обновите раздел. Текущая подтверждённая сессия основного аккаунта сохраняется для безопасного повтора; остальные сессии обоих аккаунтов отзываются.

Не передавайте код третьим лицам и не вставляйте его в тикет поддержки. Новый код отменяет предыдущий неиспользованный код исходного аккаунта.

## Что переносится

| Данные | Правило |
| --- | --- |
| Кошелёк и реферальный баланс | Суммируются в транзакции; после записи выполняется сверка, исходные остатки равны нулю |
| Подписки и VPN-связи | Все профили переходят основному аккаунту; его primary-подписка сохраняется, иначе остаётся primary исходного аккаунта |
| Платежи и финансовая история | Меняется владелец платежей, ledger, возвратов, выдачи, налогового профиля и связанных операций; суммы не пересчитываются |
| Поддержка и уведомления | Обращения, сообщения через их ticket, наблюдения, нарушения, устройства и уведомления сохраняются |
| Рефералы | Переносятся балансы, награды, ledger и дочерние связи; циклы и несовместимые родители блокируют операцию |
| Способы входа | Telegram, Яндекс, VK, email и passkeys сохраняются. Email-пароли унифицируются с паролем основного аккаунта |
| Профиль | Поля основного аккаунта имеют приоритет; пустое имя или отсутствующий основной способ входа заполняется из исходного аккаунта |
| Промо/опросы/конкурсы | История и членство переходят при отсутствии конфликтующих уникальных участий |

Исторические alias-записи входят в privacy export. При обезличивании основного аккаунта они удаляются вместе со способами входа. Старый реферальный код продолжает вести на основной аккаунт, пока аккаунт существует.

## Когда операция блокируется

Preview и финальная проверка используют одинаковые правила. Запись не начинается, если аккаунт удалён, уже объединён или ограничен; способ входа принадлежит третьему аккаунту; есть одинаковые idempotency keys, подарки, ответы на опрос, участие в конкурсе, постоянные уведомления или промогруппа; оба аккаунта имеют сохранённый способ автопродления, trial, налоговый профиль или партнёрский кабинет; итог превышает допустимую точность баланса, 10 passkeys или 20 подписок; выполняется выдача, возврат или активация подарка; реферальный граф образует цикл или имеет несовместимых родителей.

Устраните причину и создайте новый preview. Не исправляйте конфликт прямым изменением базы: уникальные ограничения и финансовый журнал являются частью защиты.

## Атомарность и повтор

`POST /api/me/account-merge/confirm` требует заголовок `Idempotency-Key`. Ключ привязывается к основному аккаунту и хэшу одноразового кода. Повтор с теми же данными возвращает сохранённый результат; повтор того же ключа с другими данными отклоняется. Пользователи блокируются в порядке ID, разрешение блокируется отдельно, а перенос и reconciliation фиксируются одной транзакцией. При конфликте или ошибке до commit не остаётся частичного переноса.

Автоматически отменить завершённое объединение нельзя. Миграция также запрещает downgrade, если уже существует история объединений. Для восстановления всей установки используйте согласованную резервную копию двух баз и файлов по [регламенту backup](BACKUP_CURRENT.md), учитывая операции после точки восстановления.

## API

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| `POST` | `/api/me/account-merge/authorization` | Повторная проверка исходного владельца и выдача одноразового кода |
| `POST` | `/api/me/account-merge/preview` | План переноса и структурированный список конфликтов |
| `POST` | `/api/me/account-merge/confirm` | Повторная проверка основного владельца, атомарный перенос и журнал результата |

Все ответы имеют `Cache-Control: private, no-store`. Маршруты защищены пользовательской сессией, CSRF для cookie-клиента и отдельными rate limits. Сырые коды и пароли не записываются в audit; событие завершения содержит только ID и количества перенесённых подписок/платежей.

## Проверка после обновления

```bash
docker compose run --rm backend alembic upgrade head
docker compose run --rm backend alembic current
docker compose exec -T backend python -m pytest -q tests/test_account_merge.py
```

Ожидаемый head — `0083_corporate_seats`. В штатном образе тесты находятся только в исходном checkout, поэтому третью команду выполняйте из CI/dev-окружения, если production-образ исключает каталог `tests`.

Для стендовой приёмки создайте два тестовых аккаунта с отдельными email и Telegram ID, добавьте остаток и подписку исходному, выполните preview и merge, затем проверьте вход обоими прежними способами, единый баланс, владельца подписок, отзыв посторонней сессии и один `account.merge.completed` в audit. Не используйте реальные персональные данные или production-платежи.

## Диагностика

Сначала сохраните результат `/health/ready`, текущий migration head и время операции. Для проверки по известным внутренним ID используйте `psql` внутри контейнера базы:

```sql
SELECT id, merged_into_user_id, merged_at, deleted_at
FROM users
WHERE id IN (:source_id, :target_id);

SELECT source_user_id, target_user_id, merged_at
FROM account_merge_aliases
WHERE source_user_id = :source_id;

SELECT source_user_id, target_user_id, result, created_at
FROM account_merge_operations
WHERE source_user_id = :source_id
ORDER BY created_at DESC;
```

Не публикуйте email, Telegram ID, cookie, Authorization, одноразовый код или полный `result`. Просроченные неиспользованные разрешения старше семи дней удаляет worker; journal успешных операций и alias-история сохраняются. Общие инфраструктурные проверки: [пошаговый регламент](INFRASTRUCTURE_CHECKS_CURRENT.md).
