# Перенос истории подписок и платежей

Раздел **Пользователи → Импорт и массовые операции → Перенос подписок и платежей** переносит из SQLite-выгрузки прежнего магазина:

- действующие и истёкшие **VPN-подписки**, уже существующие в той же панели Remnawave (по UUID пользователя Remnawave);
- **историю платежей** — для отображения клиенту и сверки.

Перенос не создаёт пользователей Remnawave и не продлевает сроки. Платежи сохраняются только как история: они не выдают доступ, не участвуют в выручке, рефералах, возвратах и сверке касс.

## Предварительные условия

1. Сделайте [согласованный backup](BACKUP_CURRENT.md) и обновитесь до head `0080_reconciliation`.
2. Сначала перенесите **профили клиентов** этого же источника ([инструкция](CUSTOMER_OPERATIONS_CURRENT.md)) с тем же «постоянным именем источника». Перенос истории находит клиентов только через эти связи. Клиент, которого нет в связях источника, блокирует перенос.
3. Подготовьте тарифы. Подписка получает тариф с тем же названием (без учёта регистра); если совпадения нет, выбирается «тариф по умолчанию». Лимиты трафика и устройств берутся из выгрузки, а при их отсутствии — из тарифа.
4. Получите в старой системе **контрольные итоги**: количество успешных и возвращённых платежей, сумму успешных платежей и количество подписок.

Право: `users.import` (роль администратора).

## Формат выгрузки (адаптер `generic-sqlite-v1`)

SQLite-файл до 5 МБ, обычные таблицы (views, virtual и вычисляемые колонки отклоняются), до 1000 строк в каждой таблице. Файл открывается только для чтения с ограничением времени и столбцов.

| Таблица | Обязательные поля | Необязательные поля |
| --- | --- | --- |
| Платежи | ID платежа, ID клиента в источнике, сумма | статус, дата оплаты, валюта, описание |
| Подписки | ID клиента в источнике, окончание, UUID пользователя Remnawave | ссылка подписки (только `https://`), название тарифа, лимит трафика (ГБ), лимит устройств |

- Сумма — рубли с копейками или копейки (выбирается); допустимо 0.01–1 000 000 с точностью до копейки.
- Статусы `paid`, `succeeded`, `success`, `completed`, `confirmed` считаются успешными, `refunded` — возвратом; остальные строки (например, `pending`, `canceled`) пропускаются и показываются в сверке отдельно.
- Даты — ISO-8601 (с часовым поясом или без) либо Unix-время в секундах/миллисекундах; хранятся в UTC.
- Валюта, если указана, должна совпадать с валютой магазина.
- Ошибочная строка (пустое поле, повтор ID платежа или UUID, неверная дата/сумма/ссылка) отклоняет весь файл с номером строки.

## Порядок работы

1. Выберите файл, укажите имя источника профилей и при необходимости тариф по умолчанию.
2. Отметьте нужные части (платежи, подписки), введите имена таблиц и нажмите «Загрузить колонки…». Подходящие колонки подставятся автоматически — проверьте их.
3. Введите контрольные итоги и нажмите **«Сверить историю»**. Сверка не изменяет данные клиентов. Результат:
   - по каждому контрольному итогу — «Совпадает» или «Расхождение» с ожидаемым и прочитанным значением;
   - статус каждой строки: «Будет перенесено», «Уже перенесено», «Конфликт данных», «Заблокировано» с причиной.
4. Применить можно, только если все итоги совпали и нет конфликтов или блокировок. Отметьте подтверждение и нажмите **«Применить историю»**. Сверка действует 30 минут и фиксирует состояние магазина: если за это время изменились клиенты или подписки, создайте новую сверку.

### Повторный перенос

Повторная загрузка того же файла не создаёт дублей: платежи узнаются по ID платежа источника, подписки — по UUID Remnawave. Совпавшие строки получают «Уже перенесено». Если платёж с тем же ID изменился (сумма, статус, клиент), строка помечается «Конфликт данных» и перенос не применяется.

### Блокировки

- клиент не найден в связях источника или удалён;
- UUID Remnawave уже привязан к подписке магазина;
- тариф не найден и тариф по умолчанию не выбран.

## Откат

В «Журнале переносов истории» у применённого переноса есть кнопка **«Откатить»** (нужна причина). Откат удаляет все платежи и подписки, созданные этим переносом, но только пока ни одна из этих подписок не изменилась и не использовалась: продление, смена тарифа, новые платежи, пробный период, подарок или подключённое устройство блокируют откат, и интерфейс показывает номера подписок. Повторный откат безопасен. После отката тот же файл можно перенести заново.

## Что видит клиент

В кабинете и Mini App в разделе «Платежи» появляется таблица «Платежи прежнего сервиса». Перенесённая подписка появляется в «Моей подписке»; если у клиента не было основной подписки, перенесённая становится основной, иначе добавляется как независимая.

## API

| Метод | Путь | Назначение |
| --- | --- | --- |
| `POST` | `/api/admin/customer-operations/history/inspect` | колонки таблицы выгрузки |
| `POST` | `/api/admin/customer-operations/history/preview` | сверка (multipart: `file`, `mapping` JSON с `control`) |
| `POST` | `/api/admin/customer-operations/history/{id}/apply` | применение (`fingerprint`) |
| `POST` | `/api/admin/customer-operations/history/{id}/cancel` | отмена сверки |
| `POST` | `/api/admin/customer-operations/history/{id}/rollback` | откат (`reason`) |
| `GET` | `/api/admin/customer-operations/history` | журнал переносов |

Нормализованные строки сверки хранятся зашифрованными до применения или истечения, исходный файл не сохраняется — только его SHA-256. Применение, откат и их итоги пишутся в журнал действий.

## Проверка

`tests/test_history_import.py` (SQLite и PostgreSQL) проверяет: сверку без записи, блокировку при расхождении итогов, повтор без дублей и конфликт изменённых строк, блокировки клиентов и UUID, устаревший preview, откат и его отказ для изменённых подписок, отклонение некорректных файлов. Браузерный сценарий — `admin/e2e/history-import.spec.ts`. Внешняя проверка на копии реальной выгрузки и стенде Remnawave остаётся за оператором.
