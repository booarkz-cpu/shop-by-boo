> Актуальная инструкция v21.5.1. head магазина `0068_network_intel`, Support Pro `0007` (3.6).

# История Support Pro после объединения и разделения

Магазин остаётся источником клиентской переписки. Merge/split выполняйте через preview/apply в магазинной админке. Изменять только локальную копию связанного обращения в Support Pro запрещено: операция не изменит каноническую историю. После магазинного переноса worker пересопоставляет сообщения и файлы по постоянным удалённым ID. Внутренние заметки, назначения и SLA Support Pro остаются локальными.

## Что исправлено

Обычный курсор новых сообщений не видит перемещённый старый ID, который меньше уже прочитанного. Теперь отдельная версия структуры изменяется только при merge/split. Она запускает полный постраничный обход, не прерываясь из-за обычных новых ответов. Версия и курсор обхода сохраняются в БД; перезапуск worker продолжает процесс. Новое изменение структуры во время обхода начинает его заново. Пока обход не закончен, локальная копия может отставать от магазина.

Постоянный `shop_message_id` отличает перенос существующего сообщения от новой записи. Связь файла перемещается вместе с сообщением, безопасный локальный файл повторно не скачивается. Владелец должен совпадать; попытка пересопоставить чужую переписку отменяет транзакцию. Namespace/origin интеграции остаются прежними.

Исходный машинный ключ доставки сохраняется отдельно от изменяемого retry key обращения. Поэтому ответ, принятый магазином перед потерей сетевого подтверждения и затем перемещённый, сопоставляется с прежней локальной отправкой. Новый outbox для такого ответа не создаётся.

## Объединённый источник и очередь

Support Pro закрывает исходное обращение и показывает ссылку на итоговое, когда оно уже синхронизировано. Старые queued/sending/failed сообщения источника переходят в `uncertain` с пояснением; задачи закрытия/открытия магазина отменяются. Новая отправка, изменение состояния и retry источника блокируются. Worker не забирает его старую очередь. Внутренние заметки можно продолжать сохранять в архивном источнике; они не отправляются клиенту.

Проверьте итоговую историю перед новой отправкой. Если магазин уже принял сообщение, очередной обход должен подтвердить его и перенести в итоговое обращение. Если сообщение не было принято, перенесите его текст вручную через новую форму итогового обращения после проверки. Старый исходный outbox автоматически не направляется в другой ticket. Файлы не переносите повторно без проверки истории.

## Обновление двух сторон

1. Объявите окно обслуживания и остановите всех writers до snapshot: backend/worker/bot магазина и Support Pro app/worker. В самостоятельном контуре остановите также его собственный бот, если он пишет в ту же БД.
2. Сделайте [согласованный backup](BACKUP_CURRENT.md) обеих БД и файлов при остановленных writers. Проверьте его восстановление на отдельном стенде; не возобновляйте writers до окончания обновления.
3. Соберите актуальные образы, выполните магазинный `alembic upgrade head` и Support Pro `python -m app.migrate` (в общем Compose — `docker compose run --rm support_migrate`). Для v28.10.0 ожидаются магазинный `0068_network_intel` и Support Pro `0007`; необходимая для remote mapping миграция `0062_support_delivery_identity` входит в цепочку магазина.
4. Запустите обновлённый API магазина, затем Support Pro и его worker. Новый реальный HTTP-клиент требует метаданные версии структуры; старый API не является совместимым для нового mapping.
5. Дождитесь полного обхода старой связанной истории. Проверяйте `/operations`, worker logs и фактические карточки. До окончания первого обхода не применяйте merge/split к старым обращениям.
6. Проверьте выбранный merge/split одного клиента, файл, итоговую карточку и приостановленную очередь источника. Внутренняя заметка должна оставаться только в исходной карточке.

Миграция 0006 сбрасывает курсоры связанной истории для первого полного обхода, сохраняя тексты/файлы. Старые `shop:<ticket>:<message>` ключи backfill-ятся в постоянные ID. Если прежняя версия уже создала исторические дубли одного удалённого ID, для mapping выбирается самая новая локальная копия; ранние копии сохраняются. Автоматического удаления исторических дублей нет: сверяйте их отдельно по backup и канонической истории. Если topology была изменена до обновления и исходный ключ доставки уже утрачен старой схемой, не повторяйте старые неопределённые отправки без ручной сверки.

## Откат и границы

Магазинная 0062 блокирует downgrade после нового переноса структуры/исходного ключа. Support Pro 0007 блокирует downgrade после заполнения версии удалённой истории или объединённого target. Восстанавливайте согласованный snapshot двух БД, uploads и исходников; не обнуляйте поля для обхода защиты.

Это синхронизация магазинной переписки. Самостоятельные email inbox и remote mapping произвольных внешних helpdesk ещё не реализованы. Внешняя production-проверка SMTP/VPN/платежей и подписанные приложения по-прежнему требуют среды владельца.
