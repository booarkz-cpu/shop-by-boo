# Выпуск v28.74.0 — этап 15: автообновление Remnawave, Automation Center, установка и CI

Дистрибутив: `v28.74.0`. Runtime/API: `21.5.1`. Head магазина: `0092_telegram_bot` (миграций нет). Support Pro: `0008` / 3.8.

## Что сделано

**Автообновление Remnawave** — «Обновления → Автообновление Remnawave» ([AUTO_UPDATE](new/AUTO_UPDATE.md))
- Панель, ноды и страница подписки, поставленные мастером, обновляются:
  - ночью в заданное время МСК (окно 2 часа, один раз за ночь);
  - или кнопкой «Обновить выбранные сейчас».
- Можно выбрать, какие установки обновлять ночью. История обновлений, итоги и новые релизы приходят в Telegram.
- Ставятся только образы, закреплённые выпуском магазина по digest и проверенные живыми тестами в CI. Это проверка совместимости перед установкой.
- Новый релиз Remnawave на GitHub виден сразу, но ставится после выпуска магазина, который его проверит.
- Версия подключённой панели сверяется с проверенной: «проверена», «новее», «старше», «не отвечает».
- Обновление идёт тем же планом, что и ручное:
  1. копия базы панели;
  2. файлы с SHA-256;
  3. закреплённые образы;
  4. `/health`;
  5. проверка HTTPS, нод и страницы подписки.
- **Откат стал полным.** Если новая панель уже запускалась, вместе с файлами возвращается база панели из копии этого обновления: новая версия могла успеть сделать миграции.

**Копия базы панели в магазине** (перенесено с этапа 10)
- Новый шаг `fetch_panel_backup` в обновлении, переустановке и удалении. Копия забирается с сервера панели и сверяется по SHA-256, шифруется AES-256-GCM ключом магазина и хранится в томе резервных копий (10 последних на сервер).
- Скачивание расшифрованной копии — с правом `backups.write`.
- Сбой этого шага действие не останавливает: копия остаётся на сервере панели, об этом пишет журнал шага.

**Automation Center** — раздел «Automation Center» ([AUTOMATION_CENTER](new/AUTOMATION_CENTER.md))
- Вся автоматика на одном экране: автообновления магазина и Remnawave, релизы на GitHub, версия панели, резервные копии, worker, оповещения.
- По каждому процессу видно состояние, расписание и последний запуск; кнопка открывает раздел, где процесс настраивается.
- Ниже — сводка «Состояния системы» с проверками, которые требуют внимания.

**Docker и установщик** ([DOCKER_GUIDE](new/DOCKER_GUIDE.md), [INSTALLATION_GUIDE](new/INSTALLATION_GUIDE.md))
- Аудит службы за службой. Тест закрепляет: у долгоживущих служб есть health check и `restart`, порты публикуют только Caddy и приём почты, данные лежат в именованных томах, обновление и откат сохраняют `.env`.
- Исправлено: ручной `scripts/rollback.sh` удалял каталог `.control`, после этого админка теряла агента автообновления.
- Агент автообновления магазина ставит установщик. Команда на сервере нужна только магазинам, поставленным раньше: службу systemd хоста контейнер не ставит, это намеренно.

**CI/CD** ([CI_CD](new/CI_CD.md))
- Тесты backend идут двумя половинами на разных машинах. Раньше один прогон занимал 25–30 минут, и на медленной машине упирался в лимит.
- Публикация мобильных пакетов ждёт перезапуска упавшего CI, а не падает сразу.
