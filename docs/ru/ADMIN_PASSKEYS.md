# Вход администратора по ключу доступа

В v21.5.1 реализованы регистрация и вход по WebAuthn в веб админке. Ключ подтверждает пользователя через PIN или биометрию устройства; браузер передаёт подписанный ответ, сервер проверяет его криптографически. Приватный ключ и биометрические данные в магазин не отправляются. Вход клиентов кабинета и native-приложений по passkey в этот модуль не входит.

## Настройка

1. Примените Alembic до `0053_admin_passkeys` и создайте проверенную резервную копию до обновления.
2. Укажите в серверном `.env` точный origin веб админки: `WEBAUTHN_ORIGIN=https://admin.example.com`. Не добавляйте завершающий `/`, путь, параметры либо домен API. Сервер определяет RP ID из hostname этого origin. CORS админки должен разрешать тот же origin; сохраните действующую настройку защищённых cookies и CSRF.
3. Перезапустите backend и worker: настройки окружения читаются при запуске. Пустой `WEBAUTHN_ORIGIN` отключает ceremonies с ответом `503`, но сохраняет ключи и альтернативные способы входа.
4. Войдите обычным способом. В разделе «Настройка магазина → Функции» включите `passkeys` (изначально выключен). Выключение этого флага блокирует новые ceremonies и входы, но не отзывает уже выданные сессии. Откройте «Безопасность → Ключи доступа», задайте название, подтвердите пароль и текущий TOTP или резервный код, если 2FA включена. Нужны права `security.passkeys` (operator/admin).
5. Нажмите «Добавить ключ доступа» и подтвердите запрос браузера. Нужен discoverable credential с user verification. Максимум десять ключей на администратора. Пароль и код очищаются в форме после попытки.
6. Выйдите. Нажмите «Войти с ключом доступа» и подтвердите PIN/биометрию. Email заранее не требуется. Сервер создаст обычную отзывную административную сессию на 30 минут и отметит подтверждение MFA.

Для локальных тестов допускается `http://localhost:8777` только при `APP_ENV=test` или `development`. Staging и production требуют HTTPS. После смены hostname существующие ключи прежнего RP не работают на новом домене: зарегистрируйте новые через обычный вход. Непрозрачный идентификатор администратора сохраняется в БД и не зависит от ротации `APP_SECRET`.

## Защита и восстановление

Challenge живёт пять минут, хранится в БД и привязан к HttpOnly cookie браузера и назначению (registration/authentication). Сервер атомарно удаляет его перед проверкой ответа; неудачная попытка также требует начать ceremony заново. Проверяются RP ID, точный origin, подпись, user presence, user verification и соответствие userHandle владельцу ключа. Cross-origin/iframe ceremonies отклоняются. Счётчик подписей хранится в bigint для полного unsigned 32-bit диапазона WebAuthn и обновляется под блокировкой PostgreSQL; синхронизируемые ключи со счётчиком `0` поддерживаются по правилам verifier.

Регистрация дополнительно требует пароль и TOTP/резервный код, чтобы одного украденного cookie было недостаточно. Изменение пароля, MFA-секрета или состояния администратора после выдачи registration challenge делает его недействительным. Отключённый/удалённый администратор не входит. Изменение роли учитывается при выдаче новой сессии и при её проверке. Создание, использование и удаление ключа записываются в аудит без публичного ключа или assertion.

Удалить собственный ключ можно в том же разделе. Существующая сессия при удалении ключа остаётся действующей: для немедленного выхода отзовите её в разделе сессий. Сохраните пароль, TOTP и резервные коды, особенно перед удалением последнего ключа. Пользовательской формы восстановления потерянного passkey нет; применяется существующий альтернативный административный вход. Регистрация не выключает пароль, Telegram или TOTP.

Downgrade `0053` блокируется, пока в `webauthn_credentials` есть ключи: откат не должен потерять устойчивые userHandle. Сначала удалите ключи контролируемым способом или применяйте исправление вперёд. Таблица challenge не содержит приватных ключей и очищается от истёкших записей при новых ceremonies.

## API

| Маршрут POST | Назначение |
| --- | --- |
| `/api/admin/auth/passkeys/registration/options` | Аутентифицированный администратор, пароль, optional OTP, название |
| `/api/admin/auth/passkeys/registration/verify` | Один ticket и браузерный registration credential |
| `/api/admin/auth/passkeys/login/options` | Discoverable authentication options без раскрытия email |
| `/api/admin/auth/passkeys/login/verify` | Один ticket, assertion и выпуск отзывной cookie-сессии |

Все четыре маршрута требуют HTTP Origin, совпадающий с конфигурацией. На аутентифицированных запросах действует существующая проверка CSRF. Responses не кэшируются. Rate limits: 5/min на каждый registration route и 8/min на каждый login route на IP; за доверенным proxy используется нормализованный адрес клиента. Инвентарь и удаление остаются в `/api/admin/v41/passkeys`.

## Проверка

Серверные тесты создают настоящий EC-ключ, COSE public key, attestation `none` и ECDSA assertions. Проверяют подпись, origin/RP, UV, userHandle, срок и повтор challenge, изменение учётных данных, отсутствие сессии после отказа. PostgreSQL-тесты проверяют одновременный replay и одинаковый sign counter по двум challenges.

Браузерный тест использует Chromium virtual authenticator: UI регистрации → выход → discoverable вход → перезагрузка → удаление. В CI это отдельный обязательный job. Это проверка приложения с виртуальным аутентификатором; поведение конкретного телефона, USB-ключа или синхронизации владельца требует отдельной проверки.

```bash
python -m pip install -r backend/requirements.txt -r backend/requirements-test.txt
cd admin
npm ci
npx playwright install chromium
npm run build
npm run test:e2e
```

Test server запускается только на loopback, использует новую in-memory SQLite и тестового администратора; не публикуйте его во внешнюю сеть.

Verifier: [py_webauthn](https://duo-labs.github.io/py_webauthn/), закреплённая версия `3.0.1`. Protocol браузерного теста: [Chrome WebAuthn](https://chromedevtools.github.io/devtools-protocol/tot/WebAuthn/).
