# Три платёжных агента

Новые подписки и пополнения кошелька создают счета только через YooKassa, RollyPay или Platega. Каталог определён в `backend/app/payment_policy.py`. Его используют выбор checkout и публичный каталог возможностей. Передача `stripe`, `paypal`, `crypto`, `apple_iap`, `google_play` или `sepa` в новом checkout отклоняется независимо от старых строк health и наличия credentials.

## Подготовка

1. Поднимите магазин и проверьте время, DNS, HTTPS и worker.
2. Используйте тестовый/staging-стенд для проверки.
3. Сохраните секреты только в серверном `.env` с доступом владельца.
4. Настройте кабинет агента и callback URLs.
5. В админ-панели включите выбранного агента и задайте приоритет.
6. Пройдите требуемую проверку допуска реальных платежей.

Реальные платежи открыты сразу, как только заданы ключи провайдера. Администратор может остановить их аварийной кнопкой. Сквозная проверка на стенде — по желанию ([E2E v2](STAGING_E2E_V2_IMPLEMENTATION.md)).

## Переменные

| Агент | Обязательные значения | Вебхук |
| --- | --- | --- |
| YooKassa | `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, `YOOKASSA_WEBHOOK_IP_ALLOWLIST` | `POST https://API_DOMAIN/api/webhooks/yookassa` |
| RollyPay | `ROLLYPAY_API_KEY`, `ROLLYPAY_SIGNING_SECRET` | `POST https://API_DOMAIN/api/webhooks/rollypay` |
| Platega | `PLATEGA_MERCHANT_ID`, `PLATEGA_SECRET` | `POST https://API_DOMAIN/api/webhooks/platega` |

`API_DOMAIN` замените фактическим доменом API. Публичный адрес агента проверяется сервером; не используйте приватные адреса для обхода проверки.

## YooKassa

1. Получите shop id и секрет в личном кабинете агента.
2. Внесите их в `.env`.
3. Укажите актуальный список IP для вебхуков агента в `YOOKASSA_WEBHOOK_IP_ALLOWLIST` по его текущей документации.
4. Зарегистрируйте HTTPS-вебхук для поддерживаемых событий оплаты и возврата.
5. Перезапустите backend/worker после изменения переменных.
6. Проверьте, что публичный каталог показывает YooKassa включённой.
7. Проверьте создание, статус, повтор callback и возврат на staging.

Автопродление работает только с сохранённым и поддерживаемым методом YooKassa. Простое сохранение произвольного токена клиентом не даёт право на автосписание.

## RollyPay

1. Получите API key и согласуйте signing secret вебхуков.
2. Настройте `.env` и HTTPS-вебхук.
3. Для тестовых счетов используйте `ROLLYPAY_TEST_MODE` согласно договору агента.
4. Сервер отправляет API key и уникальный nonce для создания операции.
5. Вебхук проверяется по подписи timestamp и исходного тела; повтор события обрабатывается идемпотентно.
6. Подтверждение сверяется через API по идентификатору, сумме, валюте и номеру заказа.

`ROLLYPAY_TEST_MODE` не равен внутреннему sandbox магазина. Для возвратов нужны согласованные `ROLLYPAY_REFUND_URL` и `ROLLYPAY_REFUND_STATUS_URL`. До их настройки не обещайте автоматический возврат.

## Platega

1. Получите merchant id и secret.
2. Настройте `.env` и callback URL.
3. Укажите нужный метод платежа согласно контракту агента.
4. Сервер проверяет заголовки callback и подтверждает операцию через API.
5. Проверьте сумму, валюту, payload заказа и повтор webhook.

Для возвратов настройте `PLATEGA_REFUND_URL` и `PLATEGA_REFUND_STATUS_URL` по условиям подключения. Ответ неизвестного внешнего формата не должен превращаться в подтверждённый возврат.

## Как выбирается агент

Из маршрута исключаются отключённые, ненастроенные и находящиеся в cooldown агенты. На новой базе приоритеты соответствуют порядку YooKassa, RollyPay, Platega. Существующие приоритеты не переписываются. Если клиент явно выбрал недоступного агента, сервер сообщает недоступность. При неопределённом результате запроса сервер не переключает клиента на второе списание вслепую.

## Кошелёк и повторные операции

Кошелёк — внутренний баланс, а не четвёртый платёжный агент. Пополнение кошелька использует тот же allowlist и проверку подтверждения. Покупка из кошелька создаёт финансовую запись и выдачу подписки через существующее ядро.

Создание платежа, покупка подарка и заявка на выплату используют `Idempotency-Key`. Сохраняйте ключ при повторе той же операции. В новом интерфейсе при ошибке сети ключ сохраняется до определённого результата. Перезагрузка браузера не сохраняет эту память: сначала проверьте историю.

## Android/iOS

Нативные клиенты сохранены, но `POST /api/payments/mobile/verify` возвращает `410`. Нельзя создавать новые платёжные записи через receipt Apple/Google. Покупатель оплачивает через три агента в кабинете. Публикация native-приложений и соответствие правилам магазинов требуют отдельной проверки; эта ветка не публикует подписанные APK/IPA.

## Исторические операции

Строки старых платежей, отчёты и возвраты не удаляются. Совместимые адаптеры и callback handlers старых агентов остаются для завершения уже созданных операций. Они не выбираются для нового checkout и не рекламируются в интерфейсе. Если такие операции есть, сохраните прежние credentials в существующем `.env` до завершения сверки. В `.env.example` новые магазины больше не получают настройки прежних агентов.

## Приёмочные сценарии

Проверьте успешную оплату, отказ, неопределённое создание, повтор с тем же ключом, webhook до ответа checkout, повтор webhook, неправильную подпись, несовпадение валюты/суммы/заказа, сбой выдачи VPN, повтор выдачи, возврат и повтор возврата. Для реальных денег нужен полный E2E с кассой и Remnawave; модульные и UI-тесты его не заменяют.


Смена тарифа, докупка трафика и возврат в кошелёк: [пошаговый регламент](WORKSPACE_COMMERCE.md).
