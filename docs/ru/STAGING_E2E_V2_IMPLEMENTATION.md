# Реализация и проверка staging E2E v2

**Статус v20.0.13:** это подробный проектный регламент. Полный runner v2 ещё не реализован; текущий выпуск не разрешает реальные платежи. Приведённый ниже итоговый контракт является целевой схемой, не текущим ответом API.

## 1. Что именно нужно исправить

Нынешний `scripts/staging-e2e.sh` вызывает внутренние `/api/internal/staging-e2e/payment`, `/verify`, `/refund`, `/refund-status` и `/remnawave`. Первый маршрут напрямую вызывает `staging_create_payment()` и **не создаёт** внутренний `Payment` через пользовательский checkout. Проверка `/verify` опрашивает провайдера, а `/remnawave` читает произвольную страницу пользователей. Значит, эти действия не доказывают получение webhook, выдачу VPN, идемпотентность или отзыв доступа после возврата. Runner печатает `[INCOMPLETE]`, сервер выставляет `full_e2e=false`, `contract_version=1`. Удалять принудительный отказ до внедрения пунктов ниже нельзя.

## 2. Отдельный стенд

1. Выделите отдельные домены HTTPS, базу PostgreSQL, Redis, панель Remnawave, пользователя и токены. Никаких общих ключей, callback URL и данных с production. Сохраните и пробно восстановите backup staging до эксперимента.
2. Задайте `APP_ENV=staging`, `PAYMENTS_SANDBOX=true`, `COOKIE_SECURE=true`. Production должен оставаться с `APP_ENV=production`, `PAYMENTS_SANDBOX=false`. Проверьте время сервера, DNS, сертификат и достижимость webhook URL извне.
3. Создайте отдельного тестового покупателя, включённый тариф с положительной ценой и sandbox credentials для каждого реально доступного провайдера. Список провайдеров задаётся явно и не бывает пустым. Если sandbox у провайдера не умеет подписанный webhook либо возврат, его нельзя сертифицировать для боевого допуска подменой mock-ответом или живым списанием.
4. Настройте в панелях провайдеров staging callback: `/api/webhooks/yookassa`, `/api/webhooks/platega`, `/api/webhooks/rollypay`. Проверьте нужные IP allowlist, подписи и время жизни подписи. Не публикуйте bearer, ключи, URL с секретами, конфигурации VPN и персональные данные в результатах.

## 3. Данные и контракт проверки

Добавьте миграцию Alembic и устойчивые записи запуска (`run_id`, `config_revision`, версия кода, времена, администратор) и случаев для провайдеров (`provider`, внутренний `Payment.id`, `order_id`, `provider_payment_id`, `user_id`, сумма/валюта, ID webhook, subscription ID, refund ID, состояния этапов). Записи связываются уникальным `run_id`; сырые секреты и данные карт не сохраняются. Сохраняйте минимальное доказательство с ограничением доступа и сроком хранения.

Каждое сохранение конфигурации должно создавать новую `revision` и runner token, закрывать gate и сбрасывать прежний результат. В v20.0.13 эта часть уже реализована. Старый запуск не должен перезаписать статус после смены конфигурации. Запуск резервируется в транзакции PostgreSQL как `queued`; конкурирующий запуск получает `409`. После падения процесса нужен явный recovery состояния `queued`/`running` с закрытым gate.

Целевой итоговый результат, который вычисляет **сервер из собственных записей**, а не скрипт или браузер:

```json
{
  "status": "passed",
  "full_e2e": true,
  "contract_version": 2,
  "config_revision": "revision-of-tested-config",
  "run_id": "random-run-uuid",
  "finished_at": "2026-09-25T12:00:00+00:00",
  "provider_results": [{
    "provider": "yookassa", "status": "passed", "payment_id": 123,
    "checks": ["checkout", "signed_webhook", "provider_match", "fulfilled", "duplicate_ignored", "refund_confirmed", "access_revoked"]
  }]
}
```

`checks` не принимаются из пользовательского JSON и не выводятся из строки `FULL_E2E_PASS`. Их вычисляют по связанным операциям магазина, полученному provider webhook и независимой сверке с провайдером и Remnawave. Пропущенный, неизвестный, отменённый или неподдерживаемый случай блокирует общий `passed`.

## 4. Шаги реализации сквозного сценария

### 4.1 Настоящий заказ магазина

Runner авторизует отдельного staging-покупателя и вызывает обычный `POST /api/payments/create` с включённым тарифом, провайдером и новым `Idempotency-Key`. Сохраняет внутренний `Payment.id`, `order_id`, snapshot цены/валюты, provider ID и HTTPS checkout. Повтор того же запроса не создаёт второй intent, заказ или списание. **Прямой** вызов `staging_create_payment()` не засчитывается. Для пополнения кошелька, подарочных карт и автопродления потребуются отдельные сценарии: один заказ тарифа их не проверяет.

Покупатель завершает оплату только в официальном sandbox checkout. Опрос статуса провайдера используется для наблюдения, но не переводит внутренний заказ в `paid`. Независимо сверяются ID, `order_id`, сумма, валюта и фактический статус оплаты; расхождение делает case `failed`.

### 4.2 Настоящий подписанный webhook

Провайдер доставляет webhook на staging URL. Существующий handler проверяет подпись/IP, связывает событие с **тем же** `Payment.id`, `run_id`, провайдерским ID и заказом и после дополнительной сверки фиксирует `Payment.status=paid`. Отметка `received_at` должна попадать в окно запуска; старые события и ответы `GET /verify` не считаются. Неверная подпись, чужой ID, сумма и валюта должны давать отказ без изменения заказа, финансового журнала или подписки.

Если приложение допускает фоновую сверку без webhook, проверяйте её отдельным case. Она не подтверждает критерий `signed_webhook`. Сохраняйте только хеш/ID события и необходимую метаинформацию, не сырое тело с секретами.

### 4.3 Выдача в Remnawave

Дождитесь `Payment.fulfillment_status=completed`, единственной связанной `Subscription`, правильного срока и лимита. По **конкретному** удалённому ID в staging Remnawave убедитесь, что доступ создан один раз и ссылка владельца работает. Чтение `/api/users?start=0&size=1` этого не доказывает. Не помещайте полную ссылку или ключ в публичный отчёт.

В контролируемом тесте временно отключите staging Remnawave: задача выдачи должна перейти в очередь повторов и завершиться после восстановления, не создав второго доступа. Production при этом не затрагивается.

### 4.4 Replay и гонки

Доставьте тот же подписанный webhook повторно штатным provider replay или санкционированной тестовой интеграцией. Сравните число `Payment`, `Subscription`, `FinancialLedger`, удалённых пользователей и срок доступа до/после. Проверьте одновременно поступившие дубликаты, поздний отказ после оплаты и success после возврата. Не обходите истёкшее окно времени подписи: тестовый replay должен иметь действительную provider-подпись.

### 4.5 Возврат и отзыв доступа

Инициируйте возврат **обычным административным маршрутом магазина** для этого `Payment`. Дождитесь подтверждения от провайдера и его уведомления, если оно поддерживается. Внутренний заказ, финансовый журнал и доступ Remnawave должны перейти в соответствующее конечное состояние; дублирующий возврат не создаёт новую операцию. Повтор старого webhook успеха после возврата не возвращает `paid` и не выдаёт VPN снова. Внутренний `/api/internal/staging-e2e/refund` без возврата внутреннего заказа не засчитывается.

### 4.6 Вычисление результата и gate

Для каждого включённого провайдера сервер проверяет **все** обязательные этапы с теми же `run_id`, `Payment.id`, `order_id`, `provider_payment_id`, пользователем и revision. Любая ошибка, таймаут, отмена либо рестарт означает `full_e2e=false`. Только после подтверждённого возврата и отзыва сервер в одной транзакции фиксирует неизменяемый `passed` и аудит. Реализуйте отрицательные сценарии до удаления `full_pass=False` из v1.

`POST /api/admin/payments/production-gate {"enabled":true}` выполняет администратор после полного результата **актуальной** конфигурации, возрастом до 24 часов и без времени из будущего. Уже сохранённый флаг перепроверяется при каждом новом платеже, пополнении и автопродлении. В v20.0.13 повторная проверка TTL/revision уже добавлена, но нынешний runner по-прежнему записывает контракт 1 и не может открыть gate.

## 5. Матрица приёмки

| Действие | Подтверждение | Провал означает |
| --- | --- | --- |
| Checkout + повтор того же ключа | Один заказ и provider intent, совпадающие деньги | `failed` |
| Sandbox оплата + webhook | Подписанное событие, provider сверка и `Payment.paid` | `failed` |
| Выдача | Одна подписка, корректные срок и лимит, удалённый доступ | `failed` |
| Повторный/параллельный webhook | Без второго заказа, продления, выдачи и финансовой записи | `failed` |
| Неверная подпись/ID/сумма/валюта | Отказ без изменения состояния | `failed` |
| Полный возврат и отзыв | Один provider refund, верное финансовое состояние, доступ отозван | `failed` |
| Success после возврата | Нет повторного `paid` и выдачи | `failed` |
| Новый revision во время run | Старый run не публикует успех, gate закрыт | `discarded` |
| Одновременные запуски | Только один `queued`/`running`, второму `409` | `failed` |
| Результат старше 24 часов/из будущего | Все новые списания блокированы | отказ допуска |
| Недоступность БД/Redis/Remnawave | Нет ложного успеха, повтор безопасен | `failed` |

Автотесты: функция расчёта v2/TTL/revision; PostgreSQL и Redis для конкуренции; подписанные webhook-фактуры; provider adapter contracts; полный цикл на отдельном staging. Для окончательного допуска повторите цикл **с настоящим sandbox провайдера**, сохраните обезличенные run ID, времена, журналы аудита и результаты независимой сверки. Mock-ответы не заменяют provider E2E.

## 6. Порядок выпуска v2

1. Внедрите миграцию и наблюдение событий при закрытом gate. Проверьте восстановление из копии. Затем внедрите связанный заказ/события/выдачу/возврат, отрицательные сценарии и вычисление результата на сервере.
2. Пройдите CI, воспроизведите сбои и реальный sandbox E2E каждого допустимого provider. Подтвердите, что sandbox credentials отличаются от боевых. Не убирайте принудительный отказ до прохождения всех критериев.
3. Выпустите **следующий** релиз с контрактом 2 и новым ключом production gate: старые флаги и результаты не должны автоматически открывать платежи. Разверните его сначала на staging, затем на production по [руководству VDS](VDS_PRODUCTION_V20_0_12.md) после проверенного backup.
4. Оператор включает gate, наблюдает очередь webhook, выдачу, возвраты и возраст проверки. Через 24 часа новые списания закрываются до свежего прогона. При инциденте сразу выключите gate, сохраните ID операций и сверьте provider и БД.

## 7. Диагностика

`[INCOMPLETE]` на текущем v1 штатен. Нет webhook — проверьте DNS, HTTPS, callback, подпись и IP; polling не засчитывается. `paid` без выдачи — проверьте worker и Remnawave по ID пользователя. `fulfilled` без безопасного replay — проверьте уникальные ограничения и блокировки. Возврат без отзыва — проверьте очередь повторов. `409` при открытии gate — проверьте версию контракта, revision, время и доказательства; текущий выпуск неизменно откажет для v1. Не правьте `staging_e2e.status` и `payments.production_gate.v20_0_8` вручную.
