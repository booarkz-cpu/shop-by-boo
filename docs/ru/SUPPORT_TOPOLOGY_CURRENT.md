# Объединение и разделение обращений — v21.5.1

Операции доступны администратору/оператору с `support.write` в магазинной админке: откройте обращение → «Объединить или разделить обращение». Требуется миграция `0056_support_topology`. Обращения разных клиентских аккаунтов объединять нельзя; незавершённый перенос Support Pro блокирует изменение истории.

## Объединение

1. Откройте исходное обращение. Выберите «Объединить в другое обращение».
2. Укажите номер итогового обращения того же клиента.
3. Нажмите «Показать preview». Проверьте клиента, номера, сообщения и число вложений.
4. Нажмите «Применить проверенную операцию».

Сообщения и вложения перемещаются атомарно, первая исходная запись и legacy reply сохраняются. ID сообщений/вложений остаются стабильными; переносимые retry keys получают namespace, чтобы не столкнуться с ключами другого обращения. Итоговое обращение открывается, исходное получает `status=merged` и `merged_into_id`.

Отправка новых сообщений/вложений в объединённый источник запрещена. Клиент и оператор видят номер итогового обращения и открывают его из списка. Исходная запись не удаляется; audit фиксирует оператора и результат.

## Разделение

1. В исходном обращении выберите «Выделить сообщения в новое».
2. Укажите тему и отметьте сообщения из загруженной истории. При необходимости загрузите следующую страницу до выбора.
3. Проверьте preview и примените его.

Новый ticket принадлежит тому же клиенту. Перемещаются только выбранные реальные message IDs и связанные с ними файлы. Начальное сообщение исходного обращения не перемещается; новая первая запись ссылается на источник. Legacy admin reply, не выбранный для переноса, остаётся в исходнике. Compatibility-проекция последнего admin reply пересчитывается.

## Повторы и конкурентные ответы

Preview содержит SHA256 конкретной истории. Новый ответ, файл или смена состояния делает его устаревшим — сервер возвращает 409, требуется новый preview. Apply использует `Idempotency-Key`; повтор того же запроса возвращает прежний target без второго перемещения. Тот же ключ с другим запросом отклоняется. PostgreSQL блокировки сериализуют операции и новые ответы.

Точные API: `POST /api/admin/support/topology/preview`, `POST /api/admin/support/topology/apply`. Поля: `kind=merge|split`, `source_id`, `target_id` для merge, `subject`/`message_ids` для split, `fingerprint` из preview для apply.

Магазинная история и вложения защищены прежними правами владельца. Это не автоматический merge внешних email inbox или самостоятельных Support Pro каналов. Связанные магазинные сообщения/файлы пересопоставляются по постоянному ID: [remote mapping](SUPPORT_REMOTE_HISTORY_CURRENT.md). Самостоятельные внешние email-каналы остаются отдельной задачей. Downgrade запрещён после появления journaled topology операций.
