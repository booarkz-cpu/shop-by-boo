# Импорт клиентов и массовые операции — v21.5.1

Раздел админки: **Пользователи → Импорт и массовые операции**. Нужна роль `admin`: права `users.import` и `users.bulk` не выданы viewer/operator. Все изменения журналируются. Схема этого модуля добавлена миграцией `0058_customer_operations`.

## Что переносится

Импорт читает обычную таблицу SQLite и сопоставляет постоянный ID строки, Telegram ID, имя и необязательный остаток кошелька. Новому Telegram-профилю можно зачислить исходный остаток. Для совпавшего Telegram ID сохраняются существующие имя, способы входа, кошелёк, рефералы и подписки; исходный остаток ему не прибавляется. Уже перенесённая строка пропускается при повторной выгрузке и после изменения `APP_SECRET`.

Email, пароли, OAuth/passkeys, токены касс и реферальные балансы/сети из сторонней схемы не импортируются. Подписки (по UUID Remnawave) и историю платежей переносит отдельный сверяемый [перенос истории](HISTORY_IMPORT_CURRENT.md) после этого шага; остальные сведения храните в защищённом архиве источника. Это перенос клиентских профилей/начальных остатков, а не автоматическое объединение аккаунтов или полный перенос любой базы другого продукта. UUID/планы/даты подписок нельзя подставить в произвольный столбец, чтобы обойти отдельную проверку VPN-миграции.

## Подготовка источника

1. Создайте согласованный backup текущего магазина по [регламенту](BACKUP_CURRENT.md), сохраните SQLite источника и остановите его новые продажи на время фактического перехода.
2. Получите snapshot через SQLite backup API. Простое копирование работающего `users.db` без WAL может пропустить подтверждённые данные. Пример на сервере старого бота:

   ```bash
   python3 - <<'PY'
   import sqlite3
   from pathlib import Path
   source_path = Path('/absolute/path/to/users.db')
   snapshot_path = Path('/absolute/path/to/users-snapshot.db')
   with sqlite3.connect(source_path.as_uri()+'?mode=ro', uri=True) as source:
       with sqlite3.connect(snapshot_path) as target:
           source.backup(target)
   snapshot_path.chmod(0o600)
   PY
   ```

   Замените оба пути. Перед созданием используйте отдельный новый файл snapshot, затем проверьте его состав. Не загружайте базу произвольного чужого сервиса.
3. Проверьте смысл баланса. `12.34` в основных единицах и `1234` в младших единицах могут означать одну сумму; выберите единицы явно. Неподтверждённый исходный остаток не зачисляйте.
4. Один snapshot содержит 1–1000 строк и занимает до 5 МБ. Отдельный баланс — 0–1000000, общий — до 10000000, точность 0.01; отрицательные остатки и NaN отклоняются. Для большого источника подготовьте последовательные выборки с тем же именем источника и неизменными ID, сохранив исходный архив. Не сокращайте идентификаторы и не переименовывайте источник ради обхода повторов.

## Проверка и применение

1. Загрузите snapshot и укажите имя обычной таблицы (по умолчанию `users`). Нажмите «Прочитать поля».
2. Задайте **постоянное имя источника**: например, `my-old-bot`. Оно обязательно остаётся одинаковым для всех повторных выгрузок этого бота. При работе с другим независимым источником используйте другое имя.
3. Выберите Telegram ID. Он должен быть положительным целым числом. Для постоянного ID строки используйте первичный ID источника; если его не выбрать, ключом станет Telegram ID. Имя и баланс необязательны.
4. Укажите единицы и валюту. Валюта должна совпадать с текущей валютой магазина. Флажок зачисления отключён по умолчанию; включает остатки **только новых** клиентов.
5. Нажмите «Проверить перенос». Просмотрите все строки, четыре категории (`new`, `existing`, `already_imported`, `blocked`), сумму и валюту. Конфликт хотя бы одной идентичности блокирует всю операцию. Несогласованный mapping/повторы ID отклоняются до создания preview.
6. Подтвердите проверку источника и примените. Preview действует 30 минут и привязан к создавшему его администратору. Новый вход/регистрация, изменение текущего клиента или другой импорт могут сделать preview устаревшим: получите новый. Никакие частичные строки не фиксируются при конфликте.
7. В истории проверьте числа новых/сопоставленных клиентов, зачисление, SHA256 snapshot и запись `customers.import.applied` в аудите. В кошельке нового клиента есть операция «Перенос начального баланса» (`wallet_import`). Клиент входит через штатную проверку Telegram; пароль ему не назначается.

Повтор того же применённого preview возвращает прежний результат. Новый preview той же выгрузки использует постоянные связи источника и не начисляет остаток второй раз. Если постоянный ID источника неожиданно привязан к другому Telegram ID, перенос останавливается. Связи с удалённым аккаунтом также не создают новый баланс автоматически: оператор сначала разбирает конфликт.

## Защита файла и данных

Файл читается через SQLite `mode=ro&immutable=1`, query-only/defensive режим, недоверенную schema, ограничения длины/колонок/времени и authorizer. Views, virtual tables, вычисляемые выбранные колонки, пользовательский SQL и расширения не выполняются. Бинарный файл находится во временном каталоге и удаляется после чтения.

В PostgreSQL preview хранит только нормализованные выбранные поля в шифрованном payload. После применения/отмены payload очищается; worker очищает истёкшие preview раз в минуту. Для этого worker должен работать. Финансовый журнал, результат, SHA256 snapshot и псевдонимизированные ключи постоянных связей сохраняются для аудита/защиты от повторов. Ответы API приватные и не кешируются публично.

## Массовые операции

Введите 1–200 разных **ID клиентов магазина**, выберите действие и укажите причину. Telegram ID вместо внутреннего ID здесь не подходит.

| Действие | Результат |
| --- | --- |
| Отозвать сессии входа | Отзываются клиентские сессии и незавершённые обмены авторизации/ссылки сброса пароля; способы входа и VPN-подписки сохраняются |
| Отключить автопродление | Отключаются флаги аккаунта и всех его подписок, очищается следующий срок автопродления; сохранённый метод оплаты остаётся, клиент может явно включить продление снова |
| Уведомление в кабинет | Каждому выбранному клиенту создаётся одно приватное in-app уведомление с текстом и заголовком; внешнее SMTP/Telegram сообщение этим действием не отправляется |

Нажмите «Проверить операцию», сверяйте полный список ID и числа клиентов/подписок/сессий, подтвердите проверку и примените. Смена данных после preview возвращает 409. Отсутствующий/удалённый клиент, повтор ID либо ошибка любой строки отменяют весь batch.

Каждый запрос применения имеет `Idempotency-Key`: точный повтор возвращает прежний результат; тот же ключ с другим запросом отклоняется. Отключение автопродления не отменяет уже созданный платёж и не делает возврат. Отзыв входа не отзывает уже выданный VPN-доступ. Для этих задач используются отдельные существующие операции.

## Обновление и откат

До обновления сохраните согласованную копию и проверьте восстановление на отдельном стенде. `0058_customer_operations` добавляет таблицы preview, постоянных связей и batch-журнала, не меняя текущие кошельки и клиентов. Downgrade блокируется после появления постоянных импортных связей или batch-журнала: удаление этих таблиц лишило бы систему защиты от повторов. Для полного отката используйте согласованный backup, сверив операции, принятые после него.

API находится под `/api/admin/customer-operations`: `import/inspect`, `import/preview`, `import/history`, `import/{id}/apply`, `import/{id}/cancel`, `bulk/preview`, `bulk/apply`. Схемы смотрите в [API-каталоге](../API_ENDPOINTS.md) и OpenAPI установленного backend.

## Ограничение и восстановление магазина (v21.5.1)

`restrict_shop` выставляет флаг ограничения, отзывает входные сессии/коды действий, отключает автопродление и очищает даты следующего списания всех выбранных подписок. Общий обработчик входа/сессии отклоняет ограниченный аккаунт. `restore_shop` снимает флаг; старые сессии и автопродление не восстанавливаются. Клиент входит заново и явно включает нужное автопродление. Обе операции имеют preview, fingerprint, обязательную причину и Idempotency-Key. Они не изменяют UUID/срок/статус VPN и не отменяют отдельную блокировку Remnawave.
