# Единая переписка магазина и Support Pro

Инструкция для v21.5.1. Магазин хранит клиентскую историю и файлы. Support Pro показывает её операторам, сохраняет назначения, SLA и внутренние заметки, а ответы передаёт через закрытый машинный API. Кабинет и админка магазина видят те же сообщения. Это дополнение к существующему SSO, а не новая система входа.

## Подключение действующей установки через Termius

Подключитесь к серверу, перейдите в каталог проекта. Для общего Docker Compose ниже используется `/opt/vpn-shop`; замените путь своим. До обновления проверьте резервные копии магазина, базы Support Pro и `support_uploads`. При самостоятельном Support Pro используйте его существующее имя Compose и volumes; не запускайте новый установщик поверх старой базы.

После получения проверенного тега и сборки образов остановите компоненты на время миграций:

```bash
cd /opt/vpn-shop
git fetch origin
git switch --detach v27
docker compose stop backend worker support_pro support_worker
docker compose build backend worker support_migrate support_pro support_worker
docker compose run --rm backend alembic upgrade head
docker compose run --rm support_migrate
```

После обновления нужны head `0062_support_delivery_identity` в магазине и `0006` в Support Pro. Схема интеграции была добавлена миграцией 0048. Корневой Compose читает существующий `support-pro/.env`. Сохраните его BOT_TOKEN, SESSION_SECRET, имя базы и настройки SSO. Для новой установки общие ключи создаёт установщик.

Настройте обе стороны одной командой, подставив **API-домен** магазина, а не домен кабинета:

```bash
python3 scripts/configure-support-bridge.py --origin https://api.example.com --instance support-main --dry-run
python3 scripts/configure-support-bridge.py --origin https://api.example.com --instance support-main
docker compose up -d backend worker support_pro support_worker
docker compose logs --tail=80 support_worker
```

Скрипт сохраняет остальные настройки, создаёт одинаковый сильный ключ в двух `.env`, ограничивает права файлов и не печатает секрет. Повтор сохраняет тот же ключ. Параметр `--instance` постоянный: смена namespace или магазина могла бы связать номера обращений с другой базой, поэтому скрипт и worker такую замену отклоняют. Для смены магазина нужен отдельный перенос связей с резервной копией.

Магазин читает `SUPPORT_BRIDGE_TOKEN`; Support Pro — `SHOP_BRIDGE_URL`, `SHOP_BRIDGE_TOKEN`, `SHOP_BRIDGE_INSTANCE`. Пустой ключ в магазине отключает API. Для самостоятельного Support Pro задайте последние три значения в его `.env` и пересоздайте app/worker. Используется публичный HTTPS origin без пути; соединение проверяет публичный DNS-адрес и запрещает redirects. Базы напрямую друг к другу не подключаются.

## Проверка оператором

1. Создайте обращение в кабинете и отправьте дополнительное сообщение с TXT-файлом.
2. Найдите его в Support Pro. В карточке указан номер обращения магазина; номера двух баз могут различаться.
3. Ответьте и проверьте тот же ответ в кабинете и админке магазина. Метка «Доставлено в кабинет» означает подтверждение API магазина. Повтор доставки использует прежний ключ.
4. Добавьте внутреннюю заметку: её не должно быть в кабинете.
5. Закройте обращение. Если параллельно пришло новое сообщение, старое закрытие не применяется: задача отменяется, оператор получает уведомление.
6. В `/operations` администратор видит последнее успешное сканирование и ошибки. Новый текст клиента снова открывает обращение.

Worker опрашивает последние 50 изменённых обращений и последовательно обходит архив страницами по 50. Переписка читается по 100 сообщений; курсор продвигается после сохранения файлов и транзакции. Полный обход обеспечивает восстановление после пропущенного или поздно завершившегося изменения. Обработка сети и большого архива может занимать больше одного 10-секундного интервала.

## Перенос старых обращений

Переносятся только **выбранные** обращения существующих Telegram-клиентов с точным совпадением Telegram ID в магазине. Аккаунты автоматически не создаются и не объединяются. Сначала сверяйте ответы со статусом queued/sending/failed/uncertain и скачайте pending-вложения. Legacy-ответ переносится как исторический текст; это не новое доказательство его доставки в Telegram.

Во время переноса остановите worker, а также приложение и бот самостоятельного Support Pro, чтобы исходная история не изменялась. В общем Compose отдельного `support_bot` нет: остановите соответствующий внешний процесс, если он запущен. Обычный магазинный бот может продолжать работать; затронутое импортируемое обращение временно не принимает новые сообщения до завершения истории.

Общий Compose, пример для старого обращения №12:

```bash
docker compose stop support_worker support_pro
docker compose run --rm --no-deps support_worker python -m app.shop_migrate --ticket-id 12
docker compose run --rm --no-deps support_worker python -m app.shop_migrate --ticket-id 12 --apply
docker compose up -d support_pro support_worker
```

Для самостоятельного Support Pro те же команды используют сервис `worker` вместо `support_worker` и выполняются в его каталоге. Preview проверяет соответствие клиента и допустимость файлов, возвращает номера и количества без текста и секретов; клиентскую историю не изменяет. Можно повторить `--ticket-id` для нескольких выбранных обращений. До `--apply` проверьте отчёт и backup.

Прерванный `--apply` повторяется с теми же ID и instance. История, даты, файлы и назначения сохраняются; внутренние заметки остаются в Support Pro. Регистрация, загрузка и каждое сообщение имеют стабильные ключи. Заключительный шаг открывает историю для обычной переписки. Новая привязка используется для дальнейших сообщений существующего связанного обращения, в том числе из прежнего бота Support Pro и его портала.

Ограничения целевого ядра: PNG, JPEG, PDF, UTF-8 TXT до 2 МБ, до трёх файлов в сообщении и двадцати в обращении. Неподдерживаемый или потерянный файл останавливает перенос **до создания** новой истории; файлы молча не исключаются. Для таких обращений требуется отдельная подготовка и сверка исходных файлов. Новые самостоятельные Telegram- и веб-обращения без созданной связи остаются в прежнем контуре, пока оператор не перенесёт их. Внешние email-каналы самостоятельно не мигрируют.

## Повторы, ошибки и откат

- Потерянный ответ API повторяется с прежним ключом. Не удаляйте связь и не меняйте instance ради повторной отправки.
- HTTP 401: проверьте одинаковость ключей. HTTP 503: интеграция магазина отключена. HTTP 409: изменились история/привязка либо перенос ещё не завершён; сверяйте карточку и состояние импорта.
- Черновики частично загруженного ответа остаются приватными; повтор worker использует прежние ключи файлов.
- `shop_status` виден в журнале задач; отменённое устаревшее закрытие не нужно повторять вручную. Неопределённый обычный Telegram-ответ требует прежней проверки дубликата; API магазина использует идемпотентный повтор.
- Объединение и разделение связанных обращений в одной локальной копии блокируется, поскольку оно нарушило бы общую историю. Это отдельная незавершённая возможность.
- После удаления аккаунта магазин отдаёт tombstone. При следующем обходе Support Pro очищает текст и файлы связанной переписки. Общая карточка клиента и его доступ в портал очищаются, если у него нет других самостоятельных обращений. Старые независимые обращения не удаляются этим запросом магазина.
- Downgrade 0048 запрещён при существующих импортных связях, downgrade 0005 — при любых связанных обращениях. Для полного возврата используйте **согласованные backup обеих баз и файлов**, а не удаление колонок. Сначала сверяйте ответы, принятые после backup.

Полный перенос других функций и внешний платёжный E2E остаются отдельной работой; состояние перечислено в WORKSPACE_COVERAGE.md.
