# Выпуск v28.34.0 — автообновление с GitHub и управление им из админ-панели

Дистрибутив: `v28.34.0`. Runtime/API: `21.5.1`. Head магазина: `0078_campaign_ab`. Support Pro: `0008` / 3.8. Мобильные приложения: 3.1.0. Дата и commit фиксируются тегом выпуска.

Установка с нуля до продакшена: [docs/INSTALLATION.md](../INSTALLATION.md). Обновления: [модуль 27](modules/27-releases-updates.md#автообновление).

## Что изменилось

**Автообновление с GitHub без участия владельца** — [INSTALLATION §9](../INSTALLATION.md#9-обновления-автодеплой-и-откат)

- Установщик спрашивает «Включить автообновление» (по умолчанию — да) и ставит агент `scripts/auto_update.py` с systemd-таймерами `vpn-shop-update` (каждую ночь в 03:00 по Москве, ±15 минут, пропущенный запуск догоняется после загрузки) и `vpn-shop-update-agent` (раз в минуту).
- Обновление идёт прежним проверенным путём `update-from-github.sh`: SHA-256 и манифест, снимок файлов, дамп базы, сборка, проверка здоровья, автоматический откат при ошибке.
- Сервер сам обращается к GitHub: SSH-ключи и секреты в GitHub не нужны.
- Выпуск, который не установился, ночью повторно не ставится. В режиме восстановления (`.rollback/RECOVERY_MODE`) автообновление остановлено до ручной проверки. Одновременно идёт не больше одного обновления (блокировка `/run/vpn-shop-update.lock`).
- Итог (обновлено, версия актуальна, ошибка с откатом) приходит в Telegram: `ALERT_TELEGRAM_CHAT_ID`, иначе `ADMIN_TELEGRAM_ID`. Хранятся 5 последних снимков.
- Сервер, обновлённый с прошлого выпуска, получает автообновление сам при сборке нового выпуска; выключенное владельцем остаётся выключенным.
- Команды на сервере: `sudo bash scripts/auto-update.sh install|status|run|disable`.

**Управление из админ-панели** — «Выпуски → Автообновление»

- Включить или выключить, время проверки по Москве, «Проверить и обновить сейчас».
- Установленная и последняя версии, статус («идёт обновление», «ожидает агента», итог), сообщение, время последнего и следующего запуска, журнал последнего запуска.
- Смотреть может оператор (`ops.releases`), менять и запускать — только администратор (`settings.runtime.write`). Каждое действие пишется в журнал аудита (`auto_update.settings`, `auto_update.run_requested`).
- Backend не выполняет команд на сервере. Панель пишет запрос в общий каталог `.control` (`/data/control` в контейнере), агент принимает из него только «включено», время в формате ЧЧ:ММ и метку запуска; каждую метку он выполняет один раз.
- API: `GET`/`PUT /api/admin/auto-update`, `POST /api/admin/auto-update/run` (409, если обновление уже идёт или уже запрошено; 503 с командой установки, если агента нет).

**Деплой из GitHub Actions**

- Если секреты `DEPLOY_*` не заданы, автоматический запуск после выпуска пропускается с пояснением вместо красной ошибки: выпуск ставит агент на сервере. Ручной запуск по-прежнему называет недостающие секреты и завершается ошибкой.
- `scripts/setup-auto-deploy.sh` готовит отдельный ключ для push-деплоя и печатает значения секретов.

**Чистые исходники и тесты**

- Из `main.py`, `admin_api.py`, `build-release.sh`, `install-vps.sh` и `build-android-apk.sh` удалены 160 строк комментариев-маркеров прошлых версий. Удалены и проверки, которые искали эти комментарии в тексте файлов: они не проверяли поведение.

## Обновление

1. Резервная копия: `bash scripts/backup.sh`.
2. Обновление на тег `v28.34.0` ([регламент](WORKSPACE_UPGRADE.md)). Миграций нет.
3. Автообновление включится само: сборка нового выпуска (`deploy/build-production.sh`) создаёт каталог `.control` и ставит агент, если на сервере его ещё нет. Если вы выключали автообновление (`auto-update.sh disable` или ответ «нет» в установщике), выбор сохраняется. Новых переменных окружения нет.
