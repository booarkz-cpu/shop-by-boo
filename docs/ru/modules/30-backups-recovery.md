# 30. Резервные копии, восстановление и аварийный режим

## Для чего

В магазине два независимых вида копий. Используйте оба.

| | Копия из панели | Полная копия `scripts/backup.sh` |
| --- | --- | --- |
| Что входит | База магазина, файлы проекта (с `.env` по выбору), медиа, мобильные пакеты | Обе базы (магазин и Support Pro), медиа, мобильные пакеты, вложения Support Pro, все `.env` |
| Не входит | База и вложения Support Pro, Redis, Remnawave | Redis, Remnawave |
| Формат | `.tar.gz` или зашифрованный `.tar.gz.enc` (AES-256-CBC, OpenSSL) | `.vpb` (AES-256-GCM, ключ из пароля через scrypt) + `.sha256` |
| Расписание | Встроенное: 6, 12 или 24 часа, хранение N копий, выгрузка в S3 | Нет, только ручной запуск или ваш cron |
| Восстановление | Из панели, двумя администраторами с 2FA | Вручную на сервере |
| Когда использовать | Ежедневная страховка основной базы | Перед обновлением, перенос на другой сервер, полная аварийная копия |

Remnawave хранит свои данные сама: делайте её копии по документации Remnawave.

## Где и кто

| Раздел | Что делает | Права |
| --- | --- | --- |
| **Безопасность → Резервные копии** | Расписание, хранение, шифрование, S3, «Создать сейчас», история с проверками и восстановлением | просмотр — `read`; настройки и создание — администратор (`manage_admins`); проверки — администратор (`backups.write`); восстановление — администратор с включённой 2FA |
| **Безопасность → Восстановление** | Центр восстановления: технический режим, состояние восстановления, worker, критические ошибки выдачи; аварийный режим | просмотр `read`; аварийный режим — администратор |

## Копии из панели

### Настройка

1. **Резервные копии** → заполните форму:
   - **Расписание** — «Выкл.», 6, 12 или 24 часа. По умолчанию выключено: включите сразу после установки;
   - **Сколько копий хранить** — от 1 до 90 (по умолчанию 7). Старые удаляются автоматически, и на сервере, и в S3;
   - **Пароль шифрования** — от 12 символов. Хранится в базе зашифрованным `APP_SECRET`. **Запишите его отдельно:** без него копию не расшифровать;
   - **Шифровать** — включено по умолчанию. Если включено «Включать .env», шифрование обязательно;
   - **Включать .env** — в копию попадают секреты сервера. Удобно для полного восстановления, но копия становится чувствительной.
2. **Внешнее хранилище (S3, R2, B2)** — сначала задайте доступ в `.env` и пересоздайте backend:

```dotenv
S3_ENDPOINT_URL=https://<account>.r2.cloudflarestorage.com
S3_BUCKET=vpn-backups
S3_REGION=auto
S3_ACCESS_KEY=...
S3_SECRET_KEY=...
BACKUP_S3_PREFIX=vpn-shop
```

```bash
cd /opt/vpn-shop && docker compose up -d --force-recreate backend
```

   Затем отметьте «Копировать во внешнее хранилище», при необходимости укажите бакет и префикс. Без переменных `.env` панель ответит «S3 is not configured in environment». После выгрузки магазин сверяет размер файла в бакете: если выгрузка не удалась, копия помечается неудачной.
3. «Сохранить», затем «Создать сейчас». В **Истории** появится запись со статусом `completed`, именем файла, SHA-256 и размером.

Копии лежат в томе `backup_data` (`/data/backups` в контейнере backend). Одновременно идёт только одна копия. О неудачной копии приходит оповещение в Telegram, если задан `ALERT_TELEGRAM_CHAT_ID` ([модуль 02](02-health-incidents-monitoring.md)), а в Prometheus растёт счётчик ошибок.

### Проверка копии

В строке копии:

- **«Проверить»** — сверяет SHA-256 файла с записанным при создании;
- **«Validate»** — расшифровывает архив во временный каталог и проверяет структуру: безопасные пути, лимиты размера, наличие `database.sql`.

Делайте обе проверки хотя бы раз в неделю и после смены пароля шифрования. Если пароль поменяли, старые копии расшифровываются только старым паролем.

Чтобы забрать копию с сервера (скачивание через API `GET /api/admin/backups/{id}/download` или по SSH):

```bash
docker compose cp backend:/data/backups/ИМЯ_ФАЙЛА ./
```

### Восстановление из панели

Восстановление перезаписывает основную базу. Нужны **два разных администратора** (роль «Администратор») с включённой 2FA. Если администратор один, используйте ручной способ ниже.

1. Администратор А: в строке копии «Запросить restore» → код 2FA. Панель покажет ID запроса. Он действует **10 минут** и привязан к этой копии и её SHA-256.
2. Передайте ID администратору Б. Он: в той же строке «Подтвердить restore» → ID → свой код 2FA.
3. Администратор А: «Restore» → подтверждение → ID → свой код 2FA.

Что делает магазин:

1. Сверяет SHA-256 копии.
2. Включает технический режим и делает **свежую копию текущего состояния** («pre-restore»): если восстановили не ту копию, вернуться можно к ней.
3. Расшифровывает архив, загружает `database.sql`, возвращает медиа и мобильные пакеты.
4. Применяет миграции до текущей версии (`alembic upgrade head`).
5. При успехе снимает технический режим. При ошибке оставляет технический режим и состояние `failed`: магазин не продаёт, пока вы не разберётесь.

Каждый шаг (запрос, подтверждение, выполнение) пишется в журнал действий и, отдельно, в `restore-audit.jsonl` в каталоге копий: этот журнал не перезаписывается восстановлением базы.

После восстановления:

- проверьте **Восстановление** (`restore_state` = `ok`), **Состояние системы**, **Очередь задач**;
- сверьте подписки с Remnawave: подписки, оплаченные после момента копии, в базе отсутствуют, а в Remnawave пользователи остались. Найдите такие платежи у провайдера и выдайте доступ вручную;
- пересоздайте сервисы, если в копии был другой `.env`: `docker compose up -d --force-recreate backend worker bot`.

### Ручное восстановление копии панели

Если администратор один или панель не запускается:

```bash
cd /opt/vpn-shop
docker compose cp backend:/data/backups/ИМЯ.tar.gz.enc /root/
umask 077 && mkdir -p /root/restore && cd /root/restore
openssl enc -d -aes-256-cbc -pbkdf2 -in /root/ИМЯ.tar.gz.enc -out backup.tar.gz   # спросит пароль
tar -tzf backup.tar.gz | head          # проверьте список
tar -xzf backup.tar.gz database.sql
cd /opt/vpn-shop
docker compose stop backend worker bot
docker compose exec -T db psql -U vpnshop -d vpnshop -v ON_ERROR_STOP=1 < /root/restore/database.sql
docker compose up -d backend worker bot
docker compose exec -T backend alembic upgrade head
```

Имя пользователя и базы возьмите из `POSTGRES_USER` и `POSTGRES_DB` в `.env`, если меняли их. После восстановления удалите `/root/restore`.

## Полная копия `scripts/backup.sh`

```bash
cd /opt/vpn-shop
sudo bash scripts/backup.sh
```

1. Скрипт спрашивает пароль (12–1024 символа). Сохраните его отдельно: восстановить нельзя. Без вопроса: `BACKUP_BUNDLE_PASSWORD=... bash scripts/backup.sh`.
2. На несколько секунд останавливает работающие сервисы, которые пишут в базы (backend, worker, bot, support_pro, support_worker), делает дампы обеих баз и снимки файлов, затем запускает их снова. Делайте копию в спокойное время.
3. Результат — `/var/backups/vpn-shop/shop-ДАТА-СЛУЧАЙНО.vpb` и `.vpb.sha256` (права 0600). Другой каталог: `BACKUP_DEST=/путь`.
4. Скрипт сам проверяет расшифровку созданного файла.
5. Скопируйте оба файла с сервера:

```bash
scp root@IP_СЕРВЕРА:/var/backups/vpn-shop/shop-*.vpb* .
```

Формат `.vpb` не загружается в восстановление панели. Восстановление — вручную по [регламенту полной копии](../BACKUP_CURRENT.md): проверить checksum, расшифровать `backup_bundle.py decrypt`, сверить `backup-manifest.json`, восстановить `shop.dump` и `support.dump` через `pg_restore`, вернуть файлы и `.env`, применить миграции.

**PostgreSQL 18.** Базы работают на PostgreSQL 18, в backend стоит клиент `pg_dump` 18. Дампы, снятые с PostgreSQL 16 до v28.23.0, восстанавливаются в PostgreSQL 18 тем же `pg_restore`; обратно (дамп 18 в сервер 16) — нет. Дамп PostgreSQL 16, сделанный при переходе, лежит в `.rollback/postgres16-<сервис>-<время>.dump`.

Регулярные полные копии можно поставить в cron, передавая пароль через файл с правами 0600, например:

```cron
30 3 * * * root BACKUP_BUNDLE_PASSWORD="$(cat /root/.backup-pass)" bash /opt/vpn-shop/scripts/backup.sh >> /var/log/vpn-backup.log 2>&1
```

Следите за кодом выхода и вывозите файлы с сервера: копия на том же диске не спасает от потери сервера.

## Учение по восстановлению

Раз в квартал проверяйте, что копии действительно восстанавливаются:

1. Поднимите отдельный сервер той же версии ([установка](../../../INSTALL_STEPS.md)).
2. Восстановите туда полную копию `.vpb`.
3. Проверьте: вход в админку, список клиентов, история платежей, обращения Support Pro, картинки.
4. Запишите время восстановления и проблемы.

Не подключайте тестовый сервер к рабочему Remnawave и платёжным провайдерам: замените их ключи в `.env` тестового сервера.

## Центр восстановления

**Безопасность → Восстановление** показывает:

| Поле | Значение |
| --- | --- |
| Технический режим | ВКЛ — покупки, пополнения и оплаты из кошелька, подарки, конкурсы и опросы отвечают 503 |
| Состояние восстановления | `ok` или `failed` после неудачного восстановления |
| Рабочий процесс heartbeat | Живы ли worker; `stale` — нет сигнала больше 90 секунд |
| Критические ошибки выдачи | Оплаты, по которым выдача окончательно не удалась |

Если включён технический режим, восстановление завершилось ошибкой или worker не отвечает, появляется предупреждение «Требуется ручная проверка». После неудачного восстановления технический режим автоматически не снимается.

### Аварийный режим

Применяйте при атаке, утечке ключей, сбое провайдера, массовых ошибках выдачи.

- **«Включить»** — переводит магазин в технический режим: новые оплаты, покупки из кошелька, подарки и конкурсы недоступны. Клиенты с подписками продолжают пользоваться VPN, админка работает.
- **«Выключить»** — снимает аварийный и технический режимы. Технический режим **остаётся**, если:
  - последнее восстановление завершилось ошибкой (`restore_state = failed`). Исправьте причину и восстановите копию заново;
  - прямо сейчас идёт восстановление;
  - в `.env` задан `MAINTENANCE_MODE=true`. Уберите его и выполните `docker compose up -d --force-recreate backend`.

Панель показывает, какой из вариантов сработал.

## Проверка

- **Резервные копии** → «Создать сейчас» → запись `completed` → «Проверить» и «Validate» успешны.
- При включённом S3 файл появился в бакете под префиксом.
- `sudo bash scripts/backup.sh` создал `.vpb` и `.sha256`; `sha256sum -c` проходит.
- **Восстановление** → «Включить» аварийный режим → тестовая покупка отвечает «Service is in maintenance mode» → «Выключить» → покупка снова работает.

## Проблемы

| Симптом | Причина | Что делать |
| --- | --- | --- |
| «Set a backup encryption password first» | Шифрование включено без пароля | Задайте пароль от 12 символов |
| «Encrypt backups when .env is included» | Нельзя хранить `.env` без шифрования | Включите шифрование или снимите «Включать .env» |
| «S3 is not configured in environment» | Нет `S3_*` в `.env` | Заполните `.env`, пересоздайте backend |
| Копия `failed` с ошибкой S3 | Неверные ключи, бакет или префикс | Проверьте доступ к бакету. Файл на сервере остаётся, но копия считается неудачной и не участвует в расписании, пока ошибка не исправлена |
| «A backup is already running» | Идёт другая копия | Дождитесь окончания |
| «Backup decryption failed» | Пароль шифрования изменили после создания копии | Используйте старый пароль (ручное восстановление) |
| «A different administrator must approve exactly once» | Подтверждает тот же администратор | Нужен второй администратор |
| «Restore approval expired…» | Прошло больше 10 минут или копия изменилась | Начните запрос заново |
| После восстановления магазин в техническом режиме | Восстановление завершилось ошибкой | Логи backend, исправьте причину, восстановите заново; потом «Выключить» аварийный режим |
