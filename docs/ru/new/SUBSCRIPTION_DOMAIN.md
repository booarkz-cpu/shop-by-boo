# Домены, сертификаты и маршруты Caddy

С v28.67.0 (этап 11). Раздел «Серверы → Домены и сертификаты» (`admin/src/domains.tsx`), backend — `backend/app/rw_domains.py`, таблица `remnawave_domains` (миграция `0091_remnawave_domains`). Закрывает модули 15 Domains, 16 Certificates и 17 Reverse Proxy из [ADMIN_CONTROL_MATRIX](ADMIN_CONTROL_MATRIX.md).

## 1. Кто обслуживает домен

| Кто | Для чего | Сертификат |
| --- | --- | --- |
| Caddy магазина | Домен портала подписки | Caddy выпускает его сам при первом обращении (on-demand), если домен включён здесь |
| Caddy сервера Remnawave | Домен панели и страницы подписки, поставленных мастером ([REMNAWAVE_INSTALLATION_WIZARD](REMNAWAVE_INSTALLATION_WIZARD.md)) | Выпускает Caddy того сервера |
| Внешний | Домен ноды (SNI) или чужого сервиса | Только проверяется |

Второго обратного прокси нет: на сервере магазина один Caddy (`deploy/Caddyfile`), на каждом сервере Remnawave — свой.

## 2. Как домен портала начинает работать без перезапуска

В `deploy/Caddyfile`:
- глобально — `on_demand_tls { ask … /caddy/ask }`;
- в конце — блок `https://` с `tls { on_demand }`: принимает любой домен, не названный выше, и отдаёт его backend как `/sub/…`.

Получив обращение к новому имени, Caddy спрашивает backend `GET /caddy/ask?domain=…`. Ответ 200 бывает только для включённого домена портала из таблицы. Тогда Caddy выпускает сертификат Let's Encrypt (HTTP-01 или TLS-ALPN-01) и дальше продлевает его сам. Любое другое имя сертификата не получает — TLS не устанавливается.

`/caddy/ask` отвечает только самому Caddy:
- запрос через прокси несёт `X-Forwarded-For`, и backend отвечает 404;
- на домене API Caddy отвечает на `/caddy/*` кодом 404, а на доменах портала любой путь превращается в `/sub/…`.

Адрес вопроса — `CADDY_ASK_URL` в `docker-compose.yml`, по умолчанию адрес backend во внутренней сети.

Домены из `SUB_PROXY_DOMAINS` в `.env` работают как раньше.

## 3. Как добавить домен портала

1. «Домены и сертификаты → Добавить домен»: домен, «Caddy магазина».
2. Запись A домена — на адрес сервера магазина (тот же, что у `API_DOMAIN`). Её можно создать кнопкой «Запись A в Cloudflare» ([§5](#5-записи-dns-через-cloudflare)) или у регистратора.
3. «Проверить» — DNS, сертификат, ответ HTTPS. Первое обращение запускает выпуск сертификата: если он ещё не готов, проверьте через минуту.
4. «Сделать адресом подписки» — клиенты получают ссылки на этом домене (адрес зеркала прослойки). Доступно только с действующим сертификатом.

Выключенный домен перестаёт получать сертификаты. Удалить нельзя домен, который сейчас служит адресом подписки.

## 4. Проверки

| Проверка | Как | Результат |
| --- | --- | --- |
| DNS | A, AAAA, CNAME, TXT, CAA через DNS-over-HTTPS (`MAIL_DNS_DOH_URL`, тот же резолвер, что у почтового домена) | `ok`, `missing` (нет A/AAAA), `mismatch` (другой адрес), `caa` (CAA запрещает Let's Encrypt), `error` |
| Ожидаемый адрес | Заданный вручную, иначе адрес сервера Remnawave, иначе адреса `API_DOMAIN` | — |
| Сертификат | TLS к адресу из DNS с доменом в SNI: издатель, срок, имена; проверка доверия | `valid`, `expiring` (меньше 14 дней), `expired`, `invalid` (не доверен), `missing` |
| HTTPS | `GET /` к тому же адресу | Код ответа |

К частному, loopback- или link-local адресу проверка не подключается: её нельзя использовать для запроса во внутреннюю сеть магазина. Соединение идёт на адрес из DNS-ответа, без второго разрешения имени.

Каждые сутки все включённые домены проверяются заново. Если сертификат истекает, истёк, не доверен или отсутствует, приходит оповещение (`send_alert`).

## 5. Записи DNS через Cloudflare

С токеном Cloudflare API (право Zone:DNS:Edit; «Настройки → Параметры → Remnawave → Токен Cloudflare API», без перезапуска) кнопка «Запись A в Cloudflare»:
- находит зону домена;
- создаёт или обновляет запись A на ожидаемый адрес IPv4, TTL 300;
- проксирование Cloudflare выключено: Let's Encrypt и VPN-клиенты должны попадать на сам сервер.

Действие пишется в журнал. Без токена кнопки нет: в результате проверки показано, какую запись создать.

**Bunny DNS и Gcore DNS (с v28.77.0).** Те же записи A создаются в зонах этих провайдеров. Ключи задаются в «Настройки → Параметры → Remnawave»: «Ключ Bunny DNS» — API key аккаунта Bunny, «Ключ Gcore DNS» — постоянный API-токен Gcore. У каждого домена появляется своя кнопка: «Запись A в Bunny DNS», «Запись A в Gcore DNS».
- **Bunny DNS.** Магазин ищет зону по самому длинному совпадению. Новая запись добавляется до того, как удаляются старые записи A того же имени, поэтому имя не остаётся без адреса. Если запись уже верная, ничего не меняется.
- **Gcore DNS.** Запись создаётся, а если уже есть — заменяется. Ключ отправляется только на `api.gcore.com`.

Идея — модуль `dns_records` из eGamesAPI/remnawave-reverse-proxy (MIT, © 2025 eGames); здесь это API магазина. Тест — `tests/test_subscription_portal.py::test_bunny_and_gcore_records`.

## 6. Сертификаты

- «Сертификаты» — список с издателем, сроком и способом продления; «Проверить все».
- Выпуск — ACME HTTP-01 или TLS-ALPN-01: порты 80 и 443 сервера должны быть открыты.
- **DNS-01 не предлагается**: нужен Caddy с модулем DNS-провайдера, а стандартный образ `caddy` его не содержит. Сборка своего образа Caddy — вместе с Docker на этапе 15. Пока для доменов с закрытым портом 80 остаётся TLS-ALPN-01 (порт 443).

## 7. Маршруты Caddy

«Маршруты Caddy» показывает, что обслуживает каждый Caddy:
- сайты магазина из `.env` (`ADMIN_DOMAIN`, `CABINET_DOMAIN`, `APP_DOMAIN`, `API_DOMAIN` и зеркала);
- домены портала (on-demand), ★ — адрес подписки;
- сайты Caddy на серверах Remnawave из успешных установок мастера.

Маршрут портала добавляется вместе с доменом. Сайты магазина меняются в `.env`: это домены самого магазина, с которыми запускаются контейнеры.

## 8. Доступ к панели Remnawave

Мастер установки может закрыть страницы панели: «Доступ к панели → Только по секретной ссылке» при установке или кнопка «Закрыть доступ к панели» у готовой установки (действие «Обновить»).

Идея — `manage_panel_access` из `eGamesAPI/remnawave-reverse-proxy` (MIT, Copyright (c) 2025 eGames), реализация своя — в построителе Caddyfile `rw_plan.caddyfile`:
- первое открытие секретной ссылки `https://<панель>/?<имя>=<значение>` ставит cookie на 30 дней;
- без cookie соединение закрывается (`abort`), как будто сервер ничего не слушает;
- открытыми остаются запросы к `/api/` с токеном (магазин, страницы панели после входа) и подписки `/api/sub/`.

Секретную ссылку показывает «Показать вход в панель».
