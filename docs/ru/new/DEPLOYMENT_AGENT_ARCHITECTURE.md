# Архитектура агента развёртывания

Часть этапа 9. Описывает, как действие из админ-панели превращается в изменения на сервере Remnawave, чтобы браузер не мог выполнить произвольную команду. Общая схема — в [REMNAWAVE_ARCHITECTURE](REMNAWAVE_ARCHITECTURE.md), API — в [REMNAWAVE_API_DESIGN](REMNAWAVE_API_DESIGN.md).

## 1. Два канала

| Канал | Когда | Как устроен | Что есть сейчас |
| --- | --- | --- | --- |
| **SSH от worker** | Первичная установка: на сервере ещё ничего нет | `paramiko`, вход по ключу или паролю. Отпечаток ключа хоста обязателен и сверяется до входа: доверия при первом подключении нет. Команды — фиксированные шаблоны, каждое значение экранировано (`shlex.quote`) | `backend/app/provisioner.py`: `_connect`, `_FingerprintPolicy`, `DOCKER_INSTALL`, `install_commands`, `node_compose` |
| **Агент на сервере** | После установки: обновления, перезапуски, копии, расширения | `scripts/node-agent.py` сам опрашивает магазин по HTTPS (`POST /api/agent/heartbeat`), входящих портов не открывает. Токен передаётся в заголовке, в базе магазина хранится его хэш | Действия `throttle`, `clear`, `update_node`, `restart_node`; терминал — только если владелец включил его на сервере (`AGENT_TERMINAL=1`) |

После успешной установки SSH больше не используется. Пароль SSH, если им входили, стирается. Дальше сервер управляется только через агента.

## 2. Шаги — закрытый список

Установка, обновление и копия раскладываются на шаги. Шаг — это тип из списка ниже и параметры строго по его схеме. Сервер строит шаги из ответов мастера; администратор видит их в плане до подтверждения. Ни браузер, ни шаг не передают на сервер текст команды. Неизвестный тип шага отклоняется и магазином, и агентом.

| Тип | Канал | Параметры | Что делает | Откат |
| --- | --- | --- | --- | --- |
| `preflight` | SSH | — | Только читает: `/etc/os-release`, `uname -m`, число CPU, память, диск, `docker version`, занятые TCP-порты, кто их слушает, разрешение доменов | Не нужен |
| `install_docker` | SSH | — | Docker из подписанного репозитория, ключ проверяется по отпечатку (`DOCKER_KEY_FINGERPRINT`) | Не удаляет Docker: он мог стоять раньше |
| `write_files` | SSH, агент | `component`, набор файлов | Записывает `docker-compose.yml`, `.env` и конфигурацию прокси, построенные магазином, в фиксированный каталог: `/opt/remnawave`, `/opt/remnanode` или `/opt/remnawave-subpage`. После записи сверяет SHA-256 | Возвращает прежние файлы из копии, сделанной перед записью |
| `compose_up` | SSH, агент | `component`, `image_digest` | `docker compose pull` и `up -d` закреплённого образа | Предыдущий digest |
| `firewall_node_port` | SSH | `panel_ip`, `node_port` | Если есть `ufw`, открывает `NODE_PORT` только для адреса панели | Удаляет добавленное правило |
| `panel_bootstrap` | SSH (через `127.0.0.1:3000`) | `admin_username` | Первый администратор панели и токен API для магазина. Пароль и токен создаются случайными, токен сохраняется зашифрованным в настройках магазина | Повтор не создаёт второго администратора: шаг проверяет, что панель уже инициализирована |
| `register_node` | API панели | `name`, `address`, `node_port`, `config_profile`, `inbounds` | `POST /api/nodes`; ключ ноды — из `GET /api/keygen` | `DELETE /api/nodes/{uuid}` |
| `install_agent` | SSH | `agent_name` | Ставит `scripts/node-agent.py` той версии, что в выпуске магазина, с проверкой SHA-256 и новым токеном | Удаляет службу агента и отзывает токен |
| `verify` | Магазин | `checks` | Проверки из CI: панель отвечает через HTTPS, нода подключилась, страница подписки отвечает | Не нужен |
| `backup_panel` | Агент | — | `pg_dump` базы `remnawave-db` внутри её контейнера, шифрование паролем копий магазина, передача в магазин | Не нужен |
| `update_component` | Агент | `component`, `image_digest` | Копия → новый образ → `verify` | Прежний digest и при необходимости восстановление копии |

Новые типы шагов добавляются только в коде магазина и агента, вместе с тестами. Из админ-панели их добавить нельзя.

**Что сделано в v28.66.0 (этап 10)** — подробно в [DEPLOYMENT_AGENT](DEPLOYMENT_AGENT.md):
- все шаги выполняются по SSH из worker; список в коде — `rw_steps.STEP_KINDS`;
- сделаны `preflight`, `install_docker`, `write_files`, `compose_up`, `firewall_node_port`, `panel_bootstrap`, `register_node`, `verify`, `backup_panel` и добавлены `wait_panel`, `restore_panel`, `compose_down`;
- `update_component` выполнен как действие «Обновить»: `backup_panel` → `write_files` → `compose_up` → `verify`; при ошибке — прежние файлы и запуск с ними;
- `install_agent` не сделан: SSH после установки остаётся каналом управления, ключ хранится зашифрованным. Агент и передача копии панели в хранилище магазина — этап 15.

## 3. Откуда берутся файлы и версии

- **Compose и `.env`** строит магазин по официальным образцам: `docker-compose-prod.yml` и `.env.sample` репозиториев `remnawave/backend`, `remnawave/node`, `remnawave/subscription-page`.
  - Значения подставляются как данные: строки — в JSON-кавычках, числа — после проверки диапазона.
  - Пример — `provisioner.node_compose`: ключ ноды не может выйти за пределы своего значения.
- **Секреты панели** (`APP_SECRET`, пароль базы, `METRICS_PASS`, пароль администратора панели, `INTERNAL_JWT_SECRET` страницы подписки; вебхуки панели выключены) создаются случайными на стороне магазина, хранятся зашифрованными и передаются только в `.env` на сервер.
- **Образы** закрепляются по digest, как образы самого магазина. Новый digest принимается, только если на этом образе прошёл живой тест в CI (`tests/live/test_remnawave_live.py`). Для этого есть workflow `resolve-image-digests.yml`.
- **Обратный прокси на сервере панели** — Caddy, та же технология, что у магазина. Отдельный сервер не конкурирует с Caddy магазина за порты 80/443. Если администратор выбирает сервер магазина, то:
  - панель там не ставится — режимы рассчитаны на отдельные VPS;
  - подписку на своём домене отдаёт существующая `sub_proxy`.

## 4. Почему не готовый установочный скрипт

Владелец ведёт свой установщик Remnawave — `booarkz-cpu/remnawave-manager`, MIT, версия 1.5.6, около 6500 строк shell. Он умеет:
- ставить «панель + ноду», «только панель» и «только ноду» без вопросов (`install single|panel|node --yes`);
- подключать расширения сторонних авторов: SelfSteal, WARP/Tor, NetBird.

Агент не запускает его целиком. Причины:
1. **Правило задания:** «не запускай исходные root-скрипты без аудита». Скрипт работает от root, ставит nginx и загружает модули других авторов с их собственными лицензиями (`CREDITS.md`).
2. **Нет шагов.** Скрипт выполняется одним куском, поэтому нельзя показать план по шагам, проверить каждый шаг и откатить именно его.
3. **Второй веб-сервер.** Скрипт ставит nginx, а у магазина единая технология прокси — Caddy.

Что из него используется: последовательность установки и рабочие значения по умолчанию. Это допускает MIT: идеи и порядок, с указанием источника там, где переносится код. Расширения сторонних авторов рассматриваются на этапе 12 по одному, с проверкой лицензии и кода.

## 5. Как агент защищён

- **Действия.** Агент принимает только типы из списка. Параметры проверяются по схеме на обеих сторонах. Каталоги, имена контейнеров и пути — фиксированные константы, а не параметры.
- **Токен.** Отдельный для каждого сервера, хранится как хэш (`node_agents.token_hash`), отзывается из панели магазина.
- **Журнал.** Вывод шагов возвращается в магазин хвостом до 4000 символов, с вырезанными секретами. Каждый шаг пишется в журнал действий с номером установки.
- **Терминал.** Агент не открывает его сам: включает только владелец сервера переменной `AGENT_TERMINAL=1` (`backend/app/node_terminal.py`). Терминал не участвует в установке.
- **Обновление агента** проходит так же, как обновление компонента: новая версия из выпуска магазина, проверка SHA-256, перезапуск службы.
