# Мастер установки Remnawave

С v28.66.0 (этап 10) панель Remnawave, ноды и страница подписки ставятся из админ-панели магазина: «Серверы → Установка Remnawave». Ручных команд на сервере не нужно. Режимы — в [REMNAWAVE_INSTALLATION_MODES](REMNAWAVE_INSTALLATION_MODES.md), проверка сервера — в [REMNAWAVE_PREFLIGHT](REMNAWAVE_PREFLIGHT.md), исполнитель — в [DEPLOYMENT_AGENT](DEPLOYMENT_AGENT.md).

## 1. Что нужно заранее

- VPS с Debian 12–13 или Ubuntu 22.04–26.04, x86_64 или arm64. Для панели — от 2 ГБ памяти и 10 ГБ свободного диска; для ноды — от 512 МБ и 5 ГБ.
- Вход по SSH: пользователь `root` или пользователь с `sudo` без пароля. Рекомендуется ключ Ed25519.
- Отпечаток ключа сервера. Его показывает хостинг в консоли или команда на сервере: `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`.
- Для сертификата Let's Encrypt — домены, которые уже указывают на сервер (запись A), и email.
- Свободные порты 80 и 443 на сервере панели и страницы подписки. Мастер не ставит Remnawave рядом с чужим веб-сервером и не трогает общий Caddy магазина.

## 2. Как пользоваться

1. **Добавить сервер.** Название, IP или имя хоста, порт SSH, пользователь, ключ или пароль, назначение (панель, нода, страница подписки). Кнопка «Получить отпечаток ключа сервера» подключается без входа и показывает отпечаток. Сохранить сервер можно, только отметив «Отпечаток совпадает».
2. **Проверить.** Вход по SSH с сохранённым отпечатком и проверка сервера (preflight). Отчёт: ОС, архитектура, CPU, память, диск, Docker, занятые порты, работающие веб-серверы, ufw. Без успешного входа сервер в мастере недоступен.
3. **Мастер.** Выбрать режим, серверы, домены, сертификат (Let's Encrypt или внутренний Caddy), порт и имя ноды, страну, правило ufw.
4. **План.** «Составить план» показывает, что изменится на каждом сервере, все шаги по порядку и образы с SHA-256. Пока план не запущен, на серверах ничего не меняется.
5. **Запуск.** «Запустить по этому плану» отправляет SHA-256 показанного плана. Если с тех пор серверы или подключение магазина изменились, запуск отклоняется: план нужно составить заново.
6. **Журнал.** В «Задачи Deployment Agent» — номер, задача, серверы, состояние, прогресс, текущий шаг, время начала и конца, ошибка. «Журнал» показывает каждый шаг с хвостом его вывода (секреты в нём заменены на `***`).
7. **После установки.**
   - «Показать вход в панель» — логин и пароль администратора панели. Каждый просмотр записывается в журнал действий.
   - «Подключить магазин к этой панели» — готовит изменение `REMNAWAVE_URL` и `REMNAWAVE_TOKEN` в настройках магазина. «Применить» включает его без перезапуска (тот же двухшаговый механизм, что в «Настройки → Параметры»). Доступно для панели с сертификатом Let's Encrypt: внутренний сертификат магазин проверить не может.

### Доступ к страницам панели

Поле «Доступ к панели» в мастере:

| Вариант | Как работает |
| --- | --- |
| Открыт по адресу панели | Страницы панели открываются по её домену, вход — логином панели |
| Только по секретной ссылке | Без секретной cookie Caddy закрывает соединение, как будто сервера нет. Ссылка — в «Показать вход в панель» |
| Вход через магазин (с v28.79.0, рекомендуется) | Страницы панели открываются только администраторам магазина с правом управлять серверами: кнопка «Открыть панель» в мастере даёт одноразовую ссылку (60 секунд), панель ставит свою cookie на 12 часов. Caddy сервера панели спрашивает магазин о каждом запросе. Вход с 2FA и passkey магазина, каждый вход — в журнале действий; «Завершить все сеансы», отключение администратора или роль без права сразу закрывают панель (с задержкой до 20 секунд). Без входа браузер попадает в админку магазина, другие клиенты получают 401. Нужен публичный адрес API магазина (`API_DOMAIN`): сервер панели должен до него доставать |
| Вход через TinyAuth (с v28.79.0) | Перед страницами панели — портал входа [TinyAuth](https://github.com/tinyauthapp/tinyauth) на своём домене (например, `auth.example.com` для `panel.example.com`: домены должны быть в одной зоне, сессия ставится на общий родительский домен). Логин `corgi` и пароль создаёт мастер, они показываются в «Показать вход в панель». Браузер без входа получает переадресацию на страницу входа, другие клиенты — 401 |

Во всех закрытых вариантах запросы магазина к API с токеном (`Authorization: Bearer …`) и подписки клиентов `/api/sub/…` проходят без входа. TinyAuth (GPL-3.0) работает отдельным контейнером `remnawave-tinyauth` рядом с Caddy, образ закреплён по SHA-256; домен входа должен указывать на сервер панели (его DNS проверяется перед установкой). Сменить вариант можно действием «Обновить».

## 3. Действия над установкой

Для успешной установки доступны кнопки. Каждая сначала составляет план, его нужно запустить отдельно.

| Кнопка | Что делает |
| --- | --- |
| Диагностика | Только читает состояние серверов и контейнеров; ничего не меняет |
| Журналы контейнеров | Последние 200 строк журнала каждого контейнера установки (с v28.79.0). Пароли, токены и ключи заменены на `***`. Ничего не меняет |
| Перезапустить / Запустить / Остановить | `docker compose restart` / `start` / `stop` контейнеров установки (с v28.79.0). Файлы и данные не меняются. Ноды останавливаются раньше панели; после запуска проверяется, что панель отвечает и ноды на связи |
| Обновить | Копия базы панели, затем те же файлы и `docker compose up` закреплённых образов, затем проверка |
| Восстановить базу панели | База панели из последней копии на её сервере |
| Переустановить | Остановка, новая запись файлов, запуск, проверка. Данные (volumes) остаются |
| Удалить | Копия базы панели, затем остановка и удаление контейнеров. Volumes и копии остаются на сервере |

Рискованные действия требуют второго нажатия. Сервер с установленными компонентами нельзя убрать из реестра, пока не выполнено «Удаление».

## 4. Права

| Действие | Право |
| --- | --- |
| Смотреть серверы, установки и журналы | `read` |
| Добавлять серверы, проверять, составлять и запускать планы, действия, вход в панель | `provision_nodes` |
| Подключить магазин к новой панели | `provision_nodes` и `settings.runtime.write` |

## 5. Что проверено

| Что | Как | Статус |
| --- | --- | --- |
| Все шаги, откат, отмена, «прерванный» исполнитель, семь режимов, действия | `tests/test_rw_installer.py` — поддельный SSH-сервер, SQLite и PostgreSQL | PASS |
| Раздел админки: реестр, отпечаток, план, журнал | `admin/e2e/rw-installer.spec.ts` — реальный backend для реестра, ответы VPS подставлены | PASS |
| Вход через магазин: без входа — в админку магазина или 401, API с токеном и подписки — без входа, одноразовая ссылка открывает панель и работает один раз | `tests/test_panel_gate.py` (SQLite и PostgreSQL: отзыв сеансов, роль, домен), `tests/live/test_panel_gate_live.py` в CI — настоящий Caddy с файлом мастера спрашивает магазин | Проверяется в CI на каждом изменении мастера |
| Вход через TinyAuth: страницы панели без входа — переадресация, API с токеном и подписки — без входа, вход с паролем мастера открывает панель, неверный — нет | `tests/live/test_tinyauth_live.py` в CI (`scripts/ci/tinyauth-live.sh`): настоящие образы TinyAuth и Caddy с файлами мастера | Проверяется в CI на каждом изменении мастера |
| «Панель + нода» по SSH на чистом сервере, закреплённые образы, обновление, удаление | `tests/live/test_install_live.py` в CI (`scripts/ci/rw-install-live.sh`): сервер CI играет роль VPS, внутренний сертификат Caddy | Проверяется в CI на каждом изменении мастера |
| Установка на настоящий VPS, Let's Encrypt с настоящим доменом, распределённая установка на несколько VPS | Нужен тестовый VPS и домен владельца | BLOCKED_EXTERNAL |

## 6. Если тестового VPS пока нет

- Мастер проверяется на поддельном SSH-сервере и в CI, где сервер CI играет роль чистого VPS. Это та же цепочка: реестр, проверка, план, запуск, шаги, проверка HTTPS через Caddy, связь ноды.
- Настоящий VPS нужен для двух вещей: сертификат Let's Encrypt (нужен домен) и сеть между разными серверами (распределённая установка, правило ufw).
- Когда VPS появится: добавить его в реестр, «Проверить», затем режим «Панель и нода» с внутренним сертификатом, затем — с Let's Encrypt.
