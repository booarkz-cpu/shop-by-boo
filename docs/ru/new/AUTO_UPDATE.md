# Автообновление магазина и Remnawave

Оба автообновления включаются, выключаются и запускаются в админке: «Система → Обновления». Сводка по ним — в [Automation Center](AUTOMATION_CENTER.md).

## Магазин

Ставит новый стабильный выпуск магазина с GitHub.

| Что | Как |
| --- | --- |
| Кто ставит | агент на сервере (`scripts/auto_update.py`, таймер systemd раз в минуту). Контейнер магазина команд на сервере не выполняет: он пишет запрос в общий каталог `.control`, агент его читает |
| Когда | каждую ночь в заданное время МСК (по умолчанию 03:00) или по кнопке «Проверить и обновить сейчас» |
| Проверка выпуска | SHA-256 архива из выпуска GitHub (`scripts/github_release_fetch.py`) |
| До установки | снимок файлов (без `.env` и `.control`) и дамп базы магазина (`scripts/update.sh`) |
| После установки | миграции, сборка, `scripts/doctor.sh` — проверка здоровья |
| При сбое | автоматический откат: прежние файлы и база из дампа; сервер помечается «режим восстановления», выпуск ночью повторно не ставится |
| Уведомление | итог — в Telegram администратору |
| Откат вручную | `sudo bash scripts/rollback.sh` (последний снимок) — с v28.74.0 сохраняет `.control`, как и обновление |

**Агент ставится установщиком сам** (`deploy/install-vps.sh`, шаг «Автообновление»). Если магазин ставился до появления агента или агент выключен командой, админка показывает подсказку. Нужна одна команда на сервере, `sudo bash /opt/vpn-shop/scripts/auto-update.sh install`, после неё всё управление идёт из админки. Из контейнера поставить службу systemd на сервере нельзя: у контейнера нет доступа к systemd сервера, и это сделано намеренно.

## Remnawave: панель, ноды, страница подписки

Обновляет то, что поставил [мастер установки](REMNAWAVE_INSTALLATION_WIZARD.md). Код — `backend/app/rw_autoupdate.py`.

### Какая версия ставится

Только образы, закреплённые в выпуске магазина по digest (`rw_plan.IMAGES`, версии — `rw_plan.VERSIONS`). Каждый выпуск магазина ставит их в CI на настоящую панель и ноду (`tests/live/test_install_live.py`, `test_node_modules_live.py`). Это и есть **проверка совместимости перед установкой**: на серверы не попадает версия, которую магазин не запускал.

Новый релиз Remnawave на GitHub виден в админке сразу (проверка каждые 6 часов или по кнопке «Проверить релизы сейчас»). Об этом приходит сообщение в Telegram, один раз на каждый релиз. Ставится он после выпуска магазина, который закрепит и проверит этот релиз. Ночное автообновление магазина приносит новые digest, следующей ночью их ставит автообновление Remnawave.

### Как ставится

Это то же действие «Обновить», что и в «Установке Remnawave», с тем же планом и журналом шагов:

1. копия базы панели на её сервере (`pg_dump -Fc`, хранятся 5 последних);
2. копия забирается в магазин, шифруется AES-256-GCM ключом магазина (`APP_SECRET`) и ложится в том резервных копий (`/data/backups/remnawave`, хранятся 10 последних на сервер). Копию больше 256 МБ магазин не забирает, она остаётся на сервере, об этом говорит журнал шага. Сбой этого шага обновление не останавливает;
3. файлы установки с проверкой SHA-256;
4. `docker compose up` закреплённых образов;
5. панель отвечает на `/health`;
6. проверка: HTTPS панели, связь нод, страница подписки.

**При сбое — автоматический откат:**
- вернутся прежние файлы, контейнеры перезапустятся с ними;
- если новая панель уже была запущена, база панели восстановится из копии этого обновления: новая версия могла успеть сделать миграции, а прежняя не читает изменённую базу.

Данные, которые панель записала между копией и откатом, при этом теряются. Это несколько минут, в которые панель и так перезапускалась.

### Расписание и выбор

| Настройка | Где | По умолчанию |
| --- | --- | --- |
| Включено | «Обновления → Автообновление Remnawave → Расписание» | выключено |
| Время (МСК) | там же; запуск в окне 2 часа после него, один раз за ночь | 04:30 — после автообновления магазина в 03:00 |
| Какие установки | там же; ничего не выбрано — все | все |
| Уведомления в Telegram | там же | включены |
| Обновить сейчас | отметить установки в таблице → «Обновить выбранные сейчас» | — |

Установка — единица обновления: «Панель и нода», отдельная нода, добавленные ноды. Ноды, добавленные отдельной установкой, обновляются отдельно от панели. Включив расписание, администратор заранее соглашается с ночными обновлениями: такие планы попадают в очередь без ручного подтверждения и видны в «Установке Remnawave» с автором `auto-update`. Пока на серверах установки идёт другое действие, обновление пропускается, об этом приходит сообщение.

### Что видно в админке

- **Версии:** проверенная магазином и последняя на GitHub для панели, ноды и страницы подписки.
- **Подключённая панель** (`REMNAWAVE_URL`): её версия (`/api/system/metadata`) против проверенной. Возможные статусы: «проверена в CI», «новее проверенной», «старше проверенной», «не отвечает».
- **Установки:** что требует обновления (панель, нода, PostgreSQL, Valkey, Caddy), последнее обновление.
- **История:** каждое обновление, кто запустил, итог, был ли откат.
- **Копии базы панели в магазине:** `GET /api/admin/remnawave/auto-update/panel-copies/<имя>`, право `backups.write`. Файл отдаётся расшифрованным (`pg_dump -Fc`), восстанавливается через `pg_restore` на сервере панели.

### API

| Метод | Путь | Право |
| --- | --- | --- |
| GET | `/api/admin/remnawave/auto-update` | `ops.releases` |
| PUT | `/api/admin/remnawave/auto-update` | `provision_nodes` |
| POST | `/api/admin/remnawave/auto-update/run` | `provision_nodes` |
| POST | `/api/admin/remnawave/auto-update/check` | `ops.releases` |
| GET | `/api/admin/remnawave/auto-update/panel-copies/{name}` | `backups.write` |

Тесты — `tests/test_rw_autoupdate.py`: ночной запуск один раз за ночь, итог в уведомлении, откат файлов и базы, объявление релиза один раз, сверка версии панели, скачивание копии. Живая проверка обновления на настоящем VPS — BLOCKED_EXTERNAL, до появления тестовых серверов. Сами образы проверяются в CI на каждом выпуске.
