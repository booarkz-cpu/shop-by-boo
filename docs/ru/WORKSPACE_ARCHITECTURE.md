# Архитектура рабочего пространства

Админка управляет магазином. Кабинет и Mini App используют один React-интерфейс. Telegram-бот и Android/iOS обращаются к тому же ядру и данным. Сторонние backend-проекты не встраиваются как параллельные финансовые ядра.

## Источники истины

| Область | Реализация |
| --- | --- |
| Клиент, подписка, платёж, кошелёк, реферал, подарок | SQLAlchemy-модели и существующая PostgreSQL-база |
| Создание и подтверждение платежа, выдача доступа | `backend/app/main.py`, `payments.py`, `worker.py` |
| Разрешённые агенты и публичные возможности | `backend/app/payment_policy.py` |
| Независимые подписки и неизменяемая привязка заказов | `subscriptions.py`, `Payment.subscription_id`, отдельные снимки устройств и триалов |
| Покупка/активация подарка | `gift_orders.py`; снимок продажи, резерв использования, повтор абсолютной выдачи |
| Проекции истории кошелька и подарков | `customer_workspace_api.py`; только записи текущего пользователя |
| Привязка реферала | `referrals.py`; одна функция для бота и кабинета |

## Устранённые дубли

Удалены неиспользуемые части `admin/src/main_src`, содержавшие вторую копию интерфейса. Next.js (static export) собирает реальный TypeScript-entry. Mini App не хранит вторую реализацию продаж, переводов и CSS: это кабинет, собранный с `NEXT_PUBLIC_SURFACE=miniapp`, с интеграцией Telegram WebApp SDK в `cabinet/src/telegram.ts`. Из обычного меню убраны дополнительные обзорные центры и отдельный вход в фиксированную карточку клиента; сведения доступны через основную главную и поиск клиента.

Два вида пользователей не объединяются механически: внутренний клиент магазина и внешний UUID Remnawave имеют разное назначение. Подарочная подписка и подарочная карта также не являются одной сущностью: первая выдаёт VPN, вторая пополняет кошелёк.

## Совместимость

Старые платежи и финансовые события не удаляются. Legacy-адаптеры не участвуют в новом checkout, но остаются для settlement/refund. Старые клиенты без ключа заявки на выплату ещё принимаются; новый интерфейс всегда передаёт его. API мобильной авторизации и VPN-компоненты сохранены, receipt purchase endpoint возвращает `410`.

Support Pro остаётся отдельным операторским компонентом. Связанные с магазином обращения, ответы, файлы и статусы синхронизируются через защищённый мост; почта и Zendesk/Freshdesk подключаются собственными каналами Support Pro (email-канал, мост helpdesk), другие внешние системы автоматически не импортируются.

## Защита интерфейса

Поздние ответы админских запросов игнорируются при смене раздела; ошибки не показывают данные прошлого экрана. Таблицы ограничивают количество отображаемых записей. В клиентских финансовых формах блокируется повторное нажатие и сохраняется ключ при неопределённом результате. Подарочные коды после использования не выдаются в проекции истории. Загруженная инструкция оператора имеет приоритет над стандартным текстом подключения.

## Проверка

Модульные контрактные проверки агентов используют поддельный транспорт без реальных списаний. Новые SQL-тесты проверяют изоляцию пользовательских данных, код подарка, повторные операции, каталог и уведомления. UI-тесты проверяют формы и сохранение состояния. Полный платёжный E2E и готовность мобильных бинарных файлов подтверждаются отдельно.

## Переписка поддержки

`support_threads.py` хранит общие правила сообщений клиента и оператора. Обе стороны используют `support_messages`; строка обращения блокируется на время проверки ключа и записи. Начальный вопрос хранится в `support_tickets.message`, последний ответ — совместимая проекция `admin_reply`. Чтение клиента проверяет владельца; административные маршруты требуют `support.read`/`support.write`. Идемпотентность ограничена обращением и ролью. Новая реплика оператора создаёт одно уведомление; клиентская реплика открывает обращение. Экспорт своих данных содержит сообщения. Приватные файлы хранятся в `support_attachments`, выдаются после проверки владельца или прав оператора и привязываются к сообщению. Публичный media-каталог для них не используется. Связанные обращения синхронизируются с Support Pro по постоянным удалённым ID.

## Операторский компонент

Support Pro сохраняет свою базу назначений, SLA и внутренних заметок. Связанная клиентская история хранится в магазине и читается через ограниченный HTTPS API с отдельным серверным ключом. Направление ответов определяется стабильной связью ticket ID; в Telegram они повторно не отправляются. Исходящие ответы и файлы используют прежние ключи при повторе. Статус изменяется с проверкой последнего сообщения; устаревшая задача отменяется. Полный обход архива дополняет выборку последних изменений и не зависит от timestamp-watermark. История переносится в два этапа с временным запретом новых записей; SourceImportLink и курсоры сохраняются в базах. Руководство: WORKSPACE_SUPPORT_BRIDGE.md.
