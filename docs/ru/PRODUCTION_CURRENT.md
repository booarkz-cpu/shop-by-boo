# Production: установка, настройка и эксплуатация v21.5.1

Это регламент для собственного VDS и собственной Remnawave. Он описывает реальные команды текущего выпуска, приёмку, обновление, резервирование и действия при сбоях. **Полный магазин пока не допущен к коммерческому запуску:** приложение не имеет завершённого payment application E2E v2, поэтому production gate закрыт. Данный документ позволяет установить и проверить инфраструктуру; он не разрешает обходить gate. Незавершённые продукты перечислены в [матрице покрытия](WORKSPACE_COVERAGE.md).

## 1. Что подготовить

Используйте отдельный Ubuntu 24.04 или Debian 12 VDS. Для первоначальной сборки нескольких frontend и Support Pro разумный стартовый запас — 4 vCPU, 8 ГБ RAM и 40 ГБ свободного диска. Это эксплуатационный ориентир, а не результат нагрузочного теста. Контролируйте нагрузку своего магазина и рост баз, файлов и копий.

Нужны root/sudo через SSH, рабочий DNS, свободные TCP 80/443, доступ к apt/GitHub/Docker registry, Telegram bot token, API token и HTTPS адрес собственной Remnawave. VPN-узлы и Remnawave Panel устанавливаются отдельно: магазин не создаёт инфраструктуру VPN за вас.

Используйте отдельные данные staging и production. Не подключайте тестовый магазин к рабочей базе, рабочим Remnawave UUID или настоящим платежным ключам. Сохраните доступ к консоли хостера на случай ошибки SSH/firewall. Не публикуйте `.env`, дампы, приватные ключи или коды 2FA в GitHub.

## 2. Домены и сеть

Пример для `vpn.example.com`:

| Назначение | Пример DNS A-записи | Обработчик |
| --- | --- | --- |
| API и callbacks | `api.vpn.example.com` → VDS IPv4 | Caddy → backend |
| Админка | `admin.vpn.example.com` → VDS IPv4 | Caddy → admin |
| Кабинет | `cabinet.vpn.example.com` → VDS IPv4 | Caddy → cabinet |
| Telegram Mini App | `app.vpn.example.com` → VDS IPv4 | Caddy → miniapp |
| Встроенный Support Pro | `support.vpn.example.com` → VDS IPv4 | Caddy → support_pro |

AAAA публикуйте только при рабочем IPv6 до этого же VDS. Параметр основного домена в установщике используется для значений по умолчанию; для публичных поверхностей нужны именно перечисленные записи. Remnawave URL может находиться на другом сервере. Публикация её через `PANEL_DOMAIN` требует отдельно работающего upstream; это не установка Remnawave.

Откройте SSH-порт, 80/443 в firewall хостера. Не открывайте PostgreSQL 5432, Redis 6379, backend 8000 или внутренние web-порты. Caddy получает TLS сертификаты при доступном DNS/HTTP. Docker published ports проверяются отдельно от UFW; текущий Compose публикует ingress, а базы остаются во внутренней сети.

## 3. SSH, Windows и Termius

В Termius создайте Host: IP VDS, свой SSH-порт, пользователь root или sudo-пользователь, SSH-ключ. Подключитесь к терминалу. В Windows cmd/PowerShell с OpenSSH:

```bash
ssh -t root@SERVER_IP
```

Замените `SERVER_IP`. Для нестандартного SSH-порта добавьте `-p PORT`. Не вставляйте пароль SSH в команду. Следующие серверные команды одинаковы для Termius и обычного SSH.

Проверьте исходную машину:

```bash
cat /etc/os-release
uname -m
df -h /
free -h
timedatectl
ss -ltnp
```

Если 80/443 заняты другим reverse proxy или сервер уже содержит магазин, не запускайте новую установку поверх него. Сначала согласуйте схему ingress либо используйте отдельный VDS.

## 4. Установка одной командой

На свежем VDS от root:

```bash
curl -fsSL https://raw.githubusercontent.com/booarkz-cpu/shop-by-boo/v27/install.sh -o /root/shop-install.sh && BRANCH=v27 bash /root/shop-install.sh
```

Установщик сам клонирует точный тег, устанавливает зависимости, собирает и запускает сервисы. Ручная распаковка ZIP не нужна. Source-каталог по умолчанию `/opt/vpn-shop-src`, рабочий каталог `/opt/vpn-shop`. Для иных каталогов задайте `SOURCE_DIR` и `APP_DIR` перед `bash`.

Docker ставится из его подписанного apt-репозитория через `deploy/install-docker.sh`. Работающий существующий Engine/Compose переиспользуется; live Engine не заменяется автоматически при отсутствии совместимого Compose plugin. Официальная процедура: [Ubuntu](https://docs.docker.com/engine/install/ubuntu/) и [Debian](https://docs.docker.com/engine/install/debian/).

Установщик запросит домены, email/пароль администратора, бот, Remnawave, платежных агентов, язык, валюту, часовой пояс, цены, параметры рефералов и OAuth. Секреты вводятся скрыто. Email для сертификата передаётся Caddy. При выборе платежей `none` аккаунты касс можно настроить позднее. `PAYMENTS_SANDBOX=true` в production запрещён.

Сохраните сгенерированные пароли магазина и Support Pro, секреты шифрования, пароль БД и коды восстановления отдельно от VDS. Не запускайте установщик повторно поверх существующего `/opt/vpn-shop`: для обновления есть отдельный маршрут. Установщик предлагает необязательный SMTP host/port/user/password/from; его можно пропустить и подключить позже. Ключи мобильной подписи настраиваются отдельно.

## 5. Проверка после установки

```bash
cd /opt/vpn-shop
docker compose config --quiet
docker compose ps -a
docker compose logs --tail=100 backend worker bot support_pro support_worker caddy
docker compose exec -T backend python -c 'from app.main import APP_VERSION; print(APP_VERSION)'
docker compose exec -T backend alembic current
docker compose exec -T support_db psql -U support -d support -Atc 'SELECT version_num FROM alembic_version'
```

Ожидается API `21.5.1`, head магазина `0062_support_delivery_identity`, Support Pro `0006`. Одноразовые init/migration контейнеры могут завершиться с кодом 0 — это штатно. Постоянные сервисы должны работать; healthcheck смотрите там, где он определён.

С другого устройства проверьте HTTPS админки, кабинета, Mini App и Support Pro. На API:

```bash
curl -fsS https://api.vpn.example.com/health/live
curl -fsS https://api.vpn.example.com/health/ready
```

Подставьте свой API-домен. `live` подтверждает процесс, `ready` — готовность зависимостей; они не доказывают оплату, доставку SMTP или работающий VPN-туннель. При ошибке проверяйте логи и readiness, не выставляйте вручную «готовность» в базе.

## 6. Первый вход и защита

Войдите в админку с данными установщика. Настройте TOTP, сохраните recovery codes, создайте отдельные operator/viewer учётные записи по необходимым правам. Регулярную работу выполняйте своей учётной записью; audit связывает действия с оператором.

Административные passkeys используют `WEBAUTHN_ORIGIN=https://admin.vpn.example.com`, клиентские — `CUSTOMER_WEBAUTHN_ORIGIN=https://cabinet.vpn.example.com`. Новая установка записывает оба origin. Для обновлённой установки добавьте их в `.env` через защищённый редактор и пересоздайте backend/worker/bot:

```bash
docker compose up -d --force-recreate backend worker bot
```

В разделе feature flags включите `passkeys`. Регистрация требует подтверждения владельца; логин — биометрию/PIN и discoverable credential. Origin должен точно совпадать с адресом страницы, без пути и завершающего `/`. Не используйте один origin для разных доменов и не меняйте RP hostname без плана переноса ключей. [Клиентская инструкция](CUSTOMER_PASSKEYS_CURRENT.md), [административная](ADMIN_PASSKEYS.md).

Клиентский WebAuthn действует в HTTPS браузере кабинета. Native API Apple/Android и WebView являются отдельными незавершёнными интеграциями; PIN приложения не равен серверной passkey-аутентификации.

## 7. Remnawave, тарифы и бот

Проверьте доступ к Remnawave с VDS, корректный API token, группы/профили, лимиты и состояние узлов. В админке создайте или проверьте тарифы: цена, дни, трафик, устройства, профиль. Для конструктора проверьте базовую цену и все варианты. Изменения тарифа не меняют уже сохранённые условия заказов.

В BotFather настройте Web App/Menu Button на свой HTTPS Mini App. Telegram initData проверяется сервером; простого знания Telegram ID недостаточно для входа. OAuth redirect URI должен соответствовать API-домену и зарегистрированному приложению. [Вход и кабинет](WORKSPACE_USER_GUIDE.md), [тарифные операции](WORKSPACE_SUBSCRIPTIONS.md).

Пробную выдачу проверяйте отдельным тестовым аккаунтом. Убедитесь, что реальные срок, UUID и лимиты в Remnawave совпадают с магазином, ссылка доступна только владельцу, выбранный VPN-клиент подключается к своему узлу. Проверьте минимум одну независимую дополнительную подписку; у неё должен быть отдельный UUID.

## 8. SMTP и восстановление аккаунта

Магазин отправляет письма через внешний SMTP; собственного MX/почтового сервера в нём нет. Введите SMTP параметры в установщике либо задайте `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM` в защищённом `.env` при последующей настройке. Кабинет должен иметь рабочий HTTPS `CABINET_URL`. Пересоздайте backend/worker, затем проверьте отправку подтверждения и password reset на свой тестовый адрес.

Отправитель и домен должны быть разрешены вашим SMTP-провайдером. SPF/DKIM/DMARC публикуются в DNS по его точным инструкциям; SMTP-настройка не создаёт входящую почту. Проверьте Inbox/Spam, одноразовость ссылок, истечение срока и отзыв сессий при смене пароля. [Подробный сценарий](WORKSPACE_ACCOUNT_SECURITY.md).

## 9. Платежи: отдельный допуск

Реализованные новые агенты — YooKassa, RollyPay и Platega. У каждого проверьте ключи, валюту, callback, подпись/IP-политику, URL возврата и URL сверки возврата. Callback принимает API-домен. Точные маршруты сверяйте с [текущим API-каталогом](../API_ENDPOINTS.md) и [инструкцией подключения](WORKSPACE_PAYMENTS.md).

Для YooKassa HTTP Basic уведомления настраиваются в кабинете провайдера. Используйте HTTPS, штатные события и опубликованный провайдером список IP; актуальная первичная инструкция — [входящие уведомления YooKassa](https://yookassa.ru/developers/using-api/webhooks). Не считайте переход браузера назад доказательством оплаты. Для Platega/RollyPay согласуйте callback/refund contract именно своего аккаунта; не подставляйте случайные URL.

**В v21.5.1 нельзя завершить допуск настоящих продаж только действиями оператора:** runner application E2E v2 ещё не реализован. Текущий runner проверяет провайдерские ответы, но не весь внутренний заказ/callback/выдачу/replay/возврат. [Точный незавершённый контракт](STAGING_E2E_V2_IMPLEMENTATION.md). Не правьте evidence или AppSetting ради открытия gate и не выдавайте unit-тесты за внешнюю приёмку.

После реализации v2 допуск потребует отдельного HTTPS стенда, тестовых касс, собственного Remnawave/SMTP, повторов callback, неверных подписей, возврата и восстановления после недоступности внешнего сервиса. Сохраните обезличенный отчёт с точным commit. Срок действительности evidence и revision проверяет сервер. Пока допуска нет, публичные страницы можно проверять, но коммерческое объявление запуска и реальные продажи следует отложить.

## 10. Рефералы и партнёры

Реферальные проценты задаются в «Обслуживание → Восстановление». До пяти уровней, суммарная ставка не более 100%; условия фиксируются при заказе. Возврат отменяет все начисленные уровни. [Рефералы](REFERRALS_CURRENT.md).

Партнёра создайте в том же разделе: название, уникальный slug, ID существующего аккаунта владельца, ставка. Его кабинет находится в клиентском меню «Партнёрский кабинет». Ссылка добавляет `?partner=slug`; новые внешние и wallet-заказы сохраняют партнёрскую ставку. Исторические платежи не пересчитываются по новой ставке. API позволяет ограничить доступные plan IDs.

Комиссия начисляется после выдачи подписки и отменяется при возврате. Выплата резервирует доступный баланс. Оператор одобряет заявку, делает внешний перевод и только затем записывает «выплачено» с номером операции. Банковский перевод приложение самостоятельно не выполняет. [Полный workflow](PARTNERS_CURRENT.md).

## 11. Поддержка

Проверьте обращение из кабинета и Mini App, ответ оператора, уведомление, приватное вложение, повтор отправки и закрытие/возобновление. Встроенный Support Pro связан с основной историей через bridge. Самостоятельные внешние email-каналы не становятся автоматически магазинными обращениями.

В админке объединение/разделение выполняется только после preview и только внутри одного клиента. Сохраняются сообщения, ID вложений и audit; устаревший preview отклоняется. [Операции с историей](SUPPORT_TOPOLOGY_CURRENT.md), [границы моста](WORKSPACE_SUPPORT_BRIDGE.md).

Для новой синхронизации после merge/split обязательны магазинная 0062 и Support Pro 0006. Обновляйте обе стороны вместе, сначала API, затем worker; дождитесь полного обхода старой истории и проверьте очередь объединённого источника. [Подробный регламент](SUPPORT_REMOTE_HISTORY_CURRENT.md).

## 12. Резервирование и restore drill

До любого обновления:

```bash
cd /opt/vpn-shop
bash scripts/backup.sh
```

Сохраните `.vpb`, `.sha256` и пароль отдельно от VDS; передайте архив через SCP/SFTP в другое хранилище. Эта копия содержит две базы, файлы и секреты окружения. Redis и состояние Remnawave резервируются/сверяются отдельно. [Полный регламент дешифрации и восстановления](BACKUP_CURRENT.md).

На отдельном изолированном VDS проверьте checksum, полную AES-GCM дешифрацию, вложенные SHA256, чтение обоих custom-format дампов и восстановление обеих баз/volumes. Тестовое окружение не должно отправлять настоящие письма, callbacks или менять рабочие VPN UUID. Убедитесь, что восстановлены исходные ключи шифрования приложения, а пароли БД согласованы с тестовыми сервисами.

После восстановления проверьте миграции, историю, суммы, приватные файлы, сессии, очередь и worker. Зафиксируйте длительность/результат восстановления. Проверка `pg_restore --list` не заменяет фактический restore. Автоматического production restore CLI нет; административные `.enc` и согласованные `.vpb` — разные форматы.

## 13. Мониторинг и ежедневные действия

Подключите `/metrics` к закрытому Prometheus, импортируйте Grafana dashboard и alerts из [набора мониторинга](OPERATIONS_MONITORING.md). Доступ к metrics ограничивается текущей серверной политикой; не делайте его публичным. Настройте свой Alertmanager/канал доставки и проверьте тестовый сигнал.

Ежедневно проверяйте readiness, worker heartbeat, очереди выдачи/возвратов/писем, возраст копии, свободный диск и состояние внешних сервисов. Финансовые расхождения разбирайте по связанным заказам и журналу. Рост `creation_unknown` требует сверки; не создавайте новый платёж вместо старого неопределённого intent.

Минимальные команды диагностики:

```bash
cd /opt/vpn-shop
docker compose ps -a
docker compose logs --since=15m --tail=200 backend worker support_pro support_worker
docker stats --no-stream
df -h
```

Логи перед передачей другим людям обезличьте. Не выполняйте `docker compose down -v` или `docker volume prune` на рабочей установке: это может удалить данные.

## 14. Обновление до v21.5.1

Сначала проверьте изолированный стенд, создайте полную согласованную копию и сохраните предыдущие исходники/окружение. Затем:

```bash
cd /opt/vpn-shop
# Для v21.5.1 с Support Pro 0006 используйте согласованное ручное обновление.
# scripts/update.sh не восстанавливает автоматически вторую БД.
```

Updater загружает проверенный GitHub архив и SHA256, сохраняет окружение и выполняет свои health/recovery проверки. Его собственный rollback snapshot включает основную базу; он не заменяет согласованный откат Support Pro. [Подробности обновления](WORKSPACE_UPGRADE.md).

Новые миграции: `0055_customer_passkeys`, `0056_support_topology`, `0062_support_delivery_identity`. Миграции не начисляют исторические комиссии. Downgrade блокируется при зарегистрированных клиентских ключах, истории объединений или финансовых партнёрских строках; используйте исправление вперёд либо согласованное восстановление исходного выпуска. После обновления повторите проверки версии/head, кабинета, поддержки, ключей и фоновых задач.

## 15. Сбой и восстановление

При проблеме выдачи остановите новые покупки штатным maintenance/incident механизмом. Проверьте состояние заказа у провайдера, затем внутренний Payment, Job и ProvisioningOperation. Не списывайте баланс повторно и не удаляйте job/ledger вручную. При подтверждённом платеже используйте штатный retry/reconcile.

Если обновление или restore завершились ошибкой, оставьте продажи закрытыми. Сохраните логи, версию, время и связанную операцию. Не запускайте одновременно старый и новый worker против одной базы. Восстанавливайте базы, файлы и окружение одной согласованной точки; после частичного восстановления одной базы нельзя считать весь магазин готовым.

TLS: проверьте A/AAAA, 80/443, логи Caddy и срок сертификата. 401: войдите заново и проверьте срок/revocation сессии. 403: проверьте роль, CSRF, точный origin или restriction; не отключайте проверки. 503 checkout: проверьте production gate, maintenance, feature flag и состояние агента. SMTP failure: проверьте отправителя, TLS/auth и журнал очереди. Ошибка passkey: проверьте HTTPS/RP origin, flag, свежесть регистрации и аккаунт; не сохраняйте ключ вручную в таблицу.

## 16. Перенос клиентов из старого бота

Перед фактическим переходом создайте согласованный backup магазина и источника, остановите новые продажи старого бота и подготовьте SQLite snapshot через backup API. В админке откройте «Клиенты → Импорт и массовые операции», сопоставьте постоянные ID/Telegram/имя/остаток, выберите единицы и валюту. Сверьте все строки и сумму preview до применения. Одинаковые выгрузки используют одно постоянное имя источника; повтор не начисляет остаток второй раз.

Новые профили могут получить начальный кошелёк; совпавшие клиенты сохраняют свои деньги и способы входа. Этот механизм не переносит чужие пароли, кассовые токены, исторические VPN-подписки и платежи. Отдельно сверяйте действующие VPN-права и историю источника перед отключением старого контура. Импорт профилей сам по себе не завершает миграцию всего магазина.

Проверьте финансовый журнал `wallet_import`, историю импортов и вход Telegram тестового клиента. Worker должен очищать истёкшие зашифрованные preview. Массовые действия дополнительно позволяют отозвать входные сессии, отключить автопродление и отправить in-app notice после проверки списка клиентов. Сохранённый метод оплаты при отключении автопродления остаётся; уже созданные платежи отдельно сверяются.

Полный регламент, пределы файла/строк/остатков, конфликты и защита отката: [импорт и массовые операции](CUSTOMER_OPERATIONS_CURRENT.md).

## 17. Публикации и персональные предложения

После обновления проверьте миграции 0059/0060 и вход admin/operator в «Новости и страницы» и «Группы и предложения». Создайте тестовый черновик, проверьте отсутствие публичного доступа, опубликуйте, измените черновик и убедитесь, что публичный текст сохраняется до новой публикации. Проверьте снятие и UTC-расписание в RU/EN. `CABINET_URL` задаёт ссылку для открытия опубликованной страницы.

Для персональной скидки используйте атомарное создание кода с аудиторией. Проверьте свой и чужой аккаунт, расчёт выбранного тарифа и резерв квоты. Задержка выдачи VPN не освобождает уже оплаченную квоту. Не удаляйте истории публикаций или правила аудитории вручную: они входят в backup, downgrade блокируется.

Полные инструкции: [контент](CONTENT_PUBLISHING_CURRENT.md), [офферы](PERSONAL_OFFERS_CURRENT.md). Массовое ограничение магазина отзывает сессии и отключает автопродление; восстановление не включает его автоматически и не отменяет отдельные VPN-ограничения антиабуза.

## 18. Дерево кнопок

После миграции 0061 проверьте совместимость старых кнопок, вложенные папки, disabled-предков, перенос и конфликт двух редакторов Mini App. Telegram custom emoji требует внешних прав бота; приложение использует безопасные статические миниатюры. MEDIA_DIR входит в backup. Downgrade блокируется при настроенном дереве. Полный регламент: [меню](MENU_TREE_CURRENT.md).

## 19. Мобильные приложения

Android/iOS исходники и CI-сборки присутствуют, но production APK/IPA требуют ключей владельца и проверенной подписи. GitHub Release содержит `mobile-production-status.json` с фактическим статусом. Не переименовывайте debug/unsigned artifact в production-пакет. [Инструкция по сборке/скачиванию](../../MOBILE.md). Native push/widget/passkeys пока не являются завершёнными функциями этого выпуска.

## 20. Критерий готовности

Работающий HTTPS и зелёный CI подтверждают только соответствующие проверки. Коммерческая приёмка дополнительно требует завершения обязательных пунктов матрицы, настоящего application E2E v2, внешнего SMTP/VPN теста, restore drill, мониторинга и подписанных приложений при их распространении. Манифест v21.5.1 сохраняет `production_ready=false`, `full_function_transfer=false`, `production_e2e_verified=false`, `signed=false`.

Документ основан на исходниках этого тега. Не используйте старые архивные инструкции как регламент текущего запуска.

Переход на Support Pro 0006 выполняйте по [согласованной процедуре обновления](WORKSPACE_UPGRADE.md): текущий автоматический rollback updater охватывает только основную БД.
