# Обновление и откат установленного магазина

Проверено 2026-11-16 по исходному коду main `4a7cb78d5fff582093aa4836aee95c4dc9da31cf`. Документ описывает существующие действия скриптов; обновление и откат VPS в рамках этой сверки не выполнялись. Цели владельца RPO 1 час / RTO 4 часа — цели, а не результаты замера.

## Перед изменением

1. Определить установленный дистрибутив по `release-manifest.template.json` и целевой стабильный тег. Версия runtime/API и версия дистрибутива различаются.
2. Проверить свежую полную зашифрованную копию `.vpb`, её checksum и возможность расшифровать отдельно хранящимся паролем. Копия должна быть доступна вне обновляемого сервера. Подробности: [полное восстановление](ru/DISASTER_RECOVERY.md), [формат текущей копии](ru/BACKUP_CURRENT.md).
3. Убедиться, что пароль копии, `APP_SECRET`, доступ к хостингу и DNS сохранены отдельно. Не отправлять `.env`, дампы и секреты в issue или логи CI.
4. Прочитать заметки целевого выпуска: изменения схемы, ограничения `min_upgrade_from`, изменения переменных и возможность восстановления старой версии. Наличие файла `latest.sql` само по себе не доказывает его пригодности.
5. Проверить свободное место для текущего дерева, SQL и Docker. `scripts/update-space.sh` оценивает бюджет, а не гарантирует место при конкурентной записи и росте образов.

Обновление не следует начинать заменой файлов через `git pull`: снимок предыдущего установленного дерева должен появиться **до** копирования нового. Так устроена штатная цепочка ниже.

## Штатная цепочка GitHub

Обычная команда на установленном сервере с `.env` в каталоге магазина:

```bash
APP_DIR=/opt/vpn-shop bash /opt/vpn-shop/scripts/update-from-github.sh
```

Для явно выбранного стабильного выпуска передают `RELEASE_TAG=vX.Y.Z` в окружении той же команды, предварительно заменив обозначение действительным тегом. Без него выбирается latest stable. Команда меняет установленный сервер; в ходе документальной сверки она не запускалась.

| Этап | Реальное действие | При отказе |
| --- | --- | --- |
| Загрузка | Установленный `scripts/github_release_fetch.py` получает release metadata, отбрасывает draft/prerelease, проверяет тег и более новую версию | Изменение установки ещё не начато |
| Проверка | Официальные адреса и разрешённые перенаправления, точное имя ZIP/checksum, SHA-256; detached manifest связывает тег, commit, runtime и дистрибутив | Нет копирования нового дерева |
| Распаковка во временный каталог | Запрещены traversal, дубликаты, ссылки и специальные файлы; ограничен размер ZIP и распакованного содержимого | Загрузка/стадирование прекращаются |
| Совместимость | `min_upgrade_from` нового пакета сравнивается с установленным дистрибутивом | Требуется промежуточный совместимый выпуск; принудительный обход не предусмотрен |
| Передача | Wrapper задаёт `UPDATE_STAGE` и запускает **установленный** `scripts/update.sh` | Его snapshot ещё относится к прежнему дереву |
| Снимки | Проверка места, tar текущих файлов и непустой SQL-дамп магазина, обновление указателей `latest.*` | Без успешного SQL обновление отменяется |
| Установка | Новое дерево копируется с исключением секретов и служебных каталогов, выполняются upgrade PostgreSQL, production build и doctor | После установки ERR trap запускает восстановление |

В базовом коде предел загрузки и суммы распакованных файлов одинаков: 80 МиБ. При сверке состава v28.158.0 обнаружено превышение распакованного бюджета; наличие всех 33 ассетов не проверяет этот предел. Исправление упаковщика и регрессия настоящего архива слиты в [PR #355](https://github.com/booarkz-cpu/shop-by-boo/pull/355), main2a204cd3: исключён только корневой screenshots/, runtime-ресурсы сохранены, оба80MiB-бюджета проверяются до атомарной замены артефакта. Готовность опубликованного нового архива и применение на VPS требуют отдельных доказательств. Исторические ассеты не заменялись.

## Что именно содержат снимки

`update.sh` устанавливает `umask 077` и создаёт в `.rollback` пару `pre-update-<UTC>.tar.gz` / `pre-update-<UTC>.sql`. `latest.tar.gz` и `latest.sql` указывают на эту пару.

Tar исключает `.git`, `.control`, `.rollback`, `node_modules` и корневые/вложенные `.env*`. SQL — обычный **незашифрованный** `pg_dump` только базы магазина с `--clean --if-exists --no-owner --no-privileges`. В нём могут быть персональные данные и секретные настройки из базы. Это не публичный диагностический артефакт. Права существующего каталога также следует проверить; один `umask` не исправляет ранее выданный доступ.

Пара не заменяет `.vpb`: не включает отдельную базу Support Pro и не является согласованной зашифрованной копией всех внешних томов, вложений и настроек. Полная копия `backup.sh` отдельно останавливает писателей на время согласованного копирования. SQL перед обновлением не гарантирует нулевую потерю записей, созданных после момента дампа.

## PostgreSQL 16 → 18 и запуск

`scripts/upgrade-postgres.sh` обнаруживает старые тома PostgreSQL16, делает dump и сверяет число строк после переноса в новые PostgreSQL18-тома для магазина и Support Pro. Маркер предотвращает повторную миграцию. Непустая новая база вызывает защитный отказ; не следует без проверки включать принудительное перезаписывание.

Старые тома не удаляются автоматически, но временный PostgreSQL16 монтирует старый том для запуска: считать его неизменяемой резервной копией нельзя. Соответствующая проверка в CI не доказывает длительность переноса конкретной production-базы.

`infrastructure/deployment/build-production.sh` переносит старые `deploy/mail-tls` в новое место при необходимости, выполняет harden-env/preflight, проверяет Compose, обновляет установку агента с сохранением выбора владельца и собирает образы. По умолчанию `FULL_REBUILD=1`, `ZERO_DOWNTIME=1`.

Standby backend сначала проверяется отдельно, затем выполняется `compose up`. Готовность `/health/ready` и HTTP главных страниц admin/miniapp/cabinet обязательны. Это не гарантия отсутствия перерывов всех служб: миграции, воркеры, поддержка и внешние системы требуют отдельной оценки. Ветка без установленного Docker прямо пишет, что runtime-прогон пропущен; её нельзя считать успешной проверкой production.

## Автоматический откат при ошибке

После создания снимков `update.sh` ставит ERR trap. Он:

1. Создаёт `.rollback/RECOVERY_MODE`, останавливает Compose вместе со standby.
2. Распаковывает прежнее дерево во временный каталог, переносит туда текущие корневые и вложенные `.env*`.
3. Заменяет установленные файлы, сохраняя `.env*`, `.git`, `.rollback`, `.control`.
4. Поднимает db/redis и восстанавливает SQL магазина с `ON_ERROR_STOP=1`.
5. Поднимает остальные службы, запускает `doctor.sh`; только после успеха удаляет маркер recovery.

Если SQL не восстановился, скрипт сообщает, что production остаётся остановленным. Наличие сообщения «update failed» не доказывает успешного отката. Если doctor не прошёл, маркер также нельзя считать разрешённым автоматически. Support Pro, внешняя панель Remnawave, ноды, DNS и сертификаты не восстанавливаются этой парой.

## Ручной откат

`scripts/rollback.sh` принимает два пути: tar дерева и SQL магазина. Без аргументов использует `.rollback/latest.tar.gz` и `.rollback/latest.sql`. Перед его запуском необходимо проверить, что выбрана согласованная пара нужной версии и сохранена полная копия текущих данных вне сервера: SQL откат перезаписывает состояние магазина.

Скрипт до остановки проверяет наличие tar, его читаемость, непустой SQL и безопасные пути через `validate-rollback-archive.py`. Проверка структуры архива не является криптографической аутентификацией SQL. Использовать можно только доверенную пару, без подмены файлов.

Затем создаётся дополнительный `pre-rollback-<UTC>.tar.gz` **кода**, но новый SQL текущей базы этот скрипт не делает. Выполняются recovery marker, остановка, перенос сохранённых `.env*`, замена дерева, восстановление SQL, production build и doctor. Старый путь `deploy/build-production.sh` поддерживается при откате до перекладки infrastructure. Удаление recovery marker означает завершение именно предусмотренных проверок, не полное тестирование бизнес-функций.

При потере сервера, обеих баз или вложений следует применять [полное восстановление](ru/DISASTER_RECOVERY.md), а не выдавать откат кода/одной базы за DR.

## Агент и проверка результата

`scripts/auto_update.py` удерживает неблокирующий файловый lock, не начинает обновление при `RECOVERY_MODE` и не повторяет один и тот же провалившийся тег при плановом запуске. После смены версии он хранит последние пять пар pre-update snapshots (`KEEP_SNAPSHOTS=5`); это не политика долговременного хранения полной копии. Выключенное владельцем автообновление сохраняется. Сообщение Telegram — уведомление с возможным отказом доставки, а не критерий восстановления.

Минимальная проверка после успешного скрипта: дистрибутив установленной версии, состояние Compose, `doctor.sh`, вход администратора/клиента, очередь и журналы без публикации секретов. Затем на согласованном тестовом окружении: состояние подписки, sandbox-заказ, поддержка и соединение настоящим VPN-клиентом. Настоящие платежи и возвраты для проверки не выполняются.

Исходники: `scripts/update-from-github.sh`, `github_release_fetch.py`, `update.sh`, `rollback.sh`, `validate-rollback-archive.py`, `upgrade-postgres.sh`, `auto_update.py`, `doctor.sh`, `infrastructure/deployment/build-production.sh`.

Регрессии в репозитории: `tests/test_exact_release_update.py`, `tests/test_distribution_update.py`, `tests/test_update_space.py`, `tests/test_auto_update_agent.py`, `tests/test_backup_bundle.py`, `scripts/ci/restore-drill.sh`. Их наличие указано как источник поведения; в этой локальной документальной сверке pytest/Docker не запускались.

Остаётся замер на выделенном VPS: длительность полного обновления, отказ в каждом опасном этапе, фактический автоматический/ручной откат, проверка обеих баз и вложений, сохранение SSH/доменов/секретов/старых путей, восстановление после потери сервера и измерение RPO/RTO. До этого инфраструктурные требования с внешней проверкой сохраняют PARTIAL/BLOCKED.
