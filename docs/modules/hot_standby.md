# Горячий резерв базы

Второй сервер с установленным магазином держит **потоковую копию** базы PostgreSQL основного сервера: отставание —
секунды, а не сутки, как у ночной копии. Если основной сервер пропадёт (сгорел диск, хостинг заблокировал, ушёл в
офлайн), резерв становится основным одной командой, и потеряны только последние секунды.

## Что нужно

* второй VPS (лучше у другого хостинга) с тем же `install.sh`; `.env` скопирован с основного **целиком** (те же
  пароли и ключи — иначе не откроются зашифрованные данные и сессии);
* открытый между серверами TCP 5432 (скрипт открывает его только для IP резерва).

## Настройка

```bash
# на основном (IP резерва — 203.0.113.10)
sudo bash scripts/hot-standby.sh primary 203.0.113.10
# скрипт напечатает команду для резерва с паролем репликации (пароль хранится в /root/corgi-standby.secret)

# на резервном
sudo REPLICATION_PASSWORD='…' bash scripts/hot-standby.sh standby 198.51.100.5
```

Что делает `primary`: роль `replicator` только с правом репликации, слот `corgi_standby` (WAL не удаляется, пока
резерв его не прочитал; предел — 20 ГБ, `max_slot_wal_keep_size`), TLS с самоподписанным сертификатом, строка
`hostssl replication` в `pg_hba.conf` только для IP резерва, порт 5432 в `docker-compose.override.yml` и правило
`DOCKER-USER` в iptables (порты Docker обходят ufw) — systemd-юнит `corgi-standby-firewall`.

Что делает `standby`: останавливает магазин на резерве, копирует базу `pg_basebackup -R` по TLS и запускает PostgreSQL
в режиме реплики. Прежние данные резерва остаются в `18/docker.old` внутри тома.

Затем в админке «Резервные копии → Горячий резерв»: отметьте «Резерв настроен» и нажмите «Команда установки агента» —
выполните её на резерве (`scripts/standby-agent.py`, systemd-таймер раз в минуту).

## Support Pro и файлы

`primary` и `standby` настраивают обе базы: магазина (`db`, порт 5432) и Support Pro (`support_db`, порт 5433), с одной
ролью репликации и одним паролем; `promote` повышает обе.

Файлы (медиа магазина, вложения поддержки, пакеты приложений) копирует агент раз в час по SSH-ключу, который может
только читать каталог томов Docker и только с IP резерва (`rrsync -ro`, `restrict`):

```bash
# на резервном
bash scripts/hot-standby.sh files-key          # напечатает команду для основного
# на основном
bash scripts/hot-standby.sh files-allow 'ssh-ed25519 AAAA… corgi-standby-files' 203.0.113.10
```

Оба сервера должны использовать один `APP_DIR` (`/opt/vpn-shop`) — имена томов совпадают.

## Учебное повышение раз в неделю

Агент раз в неделю делает копию базы резерва (`pg_basebackup` внутри контейнера), запускает её **как основную** на
порту 5499 без сети, проверяет клиентов, платежи и миграцию и удаляет. Резерв при этом продолжает следовать за основным.
Результат виден в карточке и в мобильных админках; неудача — сообщение в Telegram и оповещение. Нужно свободное место
в полтора размера базы. Вручную: `python3 /usr/local/bin/corgi-standby drill`.

## Что видно и какие оповещения

Карточка читает состояние прямо из PostgreSQL (`pg_stat_replication`, `pg_replication_slots`) и последний отчёт агента.
Оповещения в Telegram (модуль «Запуск и оповещения»): реплика не подключена; отставание больше порога; слот отключённого
резерва держит больше 5 ГБ журнала; агент молчит больше 10 минут. В «Готовности к запуску» — пункт «Горячий резерв базы».

## Когда основной пропал

Агент считает основной недоступным, только если молчат **все** пути: нет потока репликации, не отвечает
`https://API_DOMAIN/health/live`, нет TCP на 443 и 22 по IP. После `FAIL_LIMIT` минут подряд (по умолчанию 5) он пишет
в Telegram с резерва (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` в `/etc/corgi-standby.env`).

Переключение вручную (рекомендуется): `bash scripts/hot-standby.sh promote` на резерве — повышает базу, запускает весь
магазин; затем переключите DNS API, кабинета и Mini App на IP резерва. Приложения, у которых в резервных адресах API
есть второй домен (модуль «Резервные адреса API»), найдут магазин и раньше.

Автоматически: `AUTO_PROMOTE=1` в `/etc/corgi-standby.env`; с `CF_API_TOKEN`, `CF_ZONE_ID`, `CF_RECORDS` агент сам
переключит A-записи в Cloudflare.

## Риски — прочитайте до включения автоматики

* **Две основные базы (split brain).** Если основной жив, но резерв его не видит (обрыв сети между хостингами), после
  автоповышения записи пойдут в обе базы, и их уже не слить. Поэтому автоповышение выключено по умолчанию и требует
  молчания по всем путям. Вернувшийся старый основной первым делом: `bash scripts/hot-standby.sh demote` — он
  останавливает магазин, иначе бот и фоновые задачи начнут работать с двух серверов.
* После повышения резерв — одиночный сервер. Сделайте резервом бывший основной: `primary <IP старого>` на новом,
  `standby <IP нового>` на старом.
* Удаления файлов копируются тоже (`rsync --delete`); история файлов — только в обычных копиях `scripts/backup.sh`.
* Сценарий проверен тестами (правила оповещений, токен агента, синтаксис скриптов) и на PostgreSQL в CI (запросы к
  каталогу), но не на двух настоящих серверах — проведите учебное переключение до того, как оно понадобится.

API: `GET/PUT /api/admin/standby`, `POST /api/admin/standby/token`, `POST /api/standby/heartbeat` (токен агента, хранится
только хеш). Тесты: `tests/test_hot_standby.py`.
