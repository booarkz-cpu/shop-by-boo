# Приёмка iOS UI по result bundle

Требования REQ-QA-0054 и REQ-QA-0069. Приложение магазина запускается в демонстрационном режиме с фиксированными данными, без сети. Эти тесты проверяют интерфейс; изменение надписи о подключении не подтверждает настоящий VPN-туннель.

## Обязательные сценарии

Источник: [VpnShopUserUITests.swift](../apps/vpn-shop/ios/VpnShopUserUITests/VpnShopUserUITests.swift).

| Сценарий | Проверяемое поведение |
| --- | --- |
| testVpnScreenShowsConnectAndPlan | Видны кнопка подключения и текущий тариф |
| testConnectTogglesTheStatus | Кнопка меняет отображаемый статус в demo UI |
| testPremiumShowsPlans | Открывается экран тарифов |
| testGiveaways | Открывается экран розыгрыша |

Все четыре сценария должны завершиться успешно. Пропущенные тесты, expected failures, пустой или неполный отчёт не принимаются.

## Как подтверждается результат

1. `xcodebuild test` сохраняет отдельный `.xcresult` для первой попытки и, если разрешён инфраструктурный повтор, для второй.
2. `xcrun xcresulttool get test-results summary --path ...` извлекает JSON из выбранного bundle. Эта команда предусмотрена интерфейсом Xcode 16+: [Apple release notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-16_3-release-notes).
3. [verify_xcuitest_results.py](../scripts/ci/verify_xcuitest_results.py) проверяет верхний уровень JSON: result=Passed, totalTestCount=4, passedTests=4; failedTests/skippedTests/expectedFailures=0; пустой testFailures. Счётчики должны быть целыми неотрицательными числами; bool и строки отклоняются.
4. Проверка создаёт `xcuitest-verified.json` с реальным verdict, commit/head SHA, branch, run ID/attempt, числом тестов и границей охвата. При неуспехе прежний success proof заменяется отрицательным результатом.
5. Workflow сохраняет извлечённый summary, verdict и логи как GitHub Actions artifact на 14 дней, включая неуспешный запуск. Исходный бинарный bundle остаётся временным файлом runner; его нельзя обещать после завершения job.

Повтор разрешён только при уже существующих диагностических признаках сбоя запуска симулятора и отсутствии XCTAssert в логе. При ошибке assertion повтор не добавляется; выбранный результат повторной попытки проверяется так же строго. Старый bundle не используется как fallback.

## Граница доказательств

В CI 44164562114 job 134327050893 получил SUCCESS, но доступный текстовый лог содержит только три завершённых test cases и начало четвёртого, без итогового summary. Это пробел доказательств, а не установленная причина ложного SUCCESS: одного текстового лога недостаточно для такого вывода. Новая проверка исключает принятие неполного result bundle; её реальную совместимость должен подтвердить новый запуск на macos-26-intel.

Стандартный Intel runner и отдельные arm64-сборки приложений/расширений сохранены. Реальные платежи, VPN, физические устройства, подписи, полнота остальных экранов и скриншотная приёмка сюда не входят. Полная готовность проекта остаётся неподтверждённой; F-006 также остаётся открытой.

[Негативные проверки валидатора](../tests/test_xcuitest_results.py) используют parser fixtures. Это доказательство поведения барьера, а не выполнение XCUITest. При добавлении или удалении обязательного сценария нужно осознанно обновить expected-tests и таблицу сценариев.
